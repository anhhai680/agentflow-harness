# Agentflow playbook

How to run `agentflow` in a repository with Claude Code or Codex. It is a task guide: follow it top to bottom the first time, then use the cheat sheet in section 10.

This repo is the reference setup: its own pack is `.agentflow/config.yaml`. The design is in `docs/agentflow-harness-proposal.md`, the build records are in `docs/plans/`, and `ARCHITECTURES.md` at the repository root maps the engine's modules and how a run flows through them. This playbook does not repeat them. It tells you what to type and what to check.

## 1. What agentflow does for you

`agentflow` walks one main workflow without you typing each skill: `define → plan → build → verify → review → ship`.

- Each **phase** has several **steps**, and each step maps to one skill.
- A **lane** names the kind of work and selects which steps run. The engine's defaults and this repository's pack have two, `feature` and `bug`. A pack may define more: the engine's `python` test fixture pack adds `eval` and `design` (section 7). A phase with no step for the lane is skipped with no approval. The CLI uses lane names. The dashboard shows one workflow and asks "What kind of work?" in plain words instead (`dashboard.backlog.lane_labels`).

- Each agent step is **one headless call** (`claude -p …` or `codex exec …`) with one skill and one prompt. It writes a result file and exits.
- **Shell gates** (the pack's `gates`: lint, types, tests and so on) run after the steps that name them. A failing gate resumes the same session with the output, up to `defaults.fix_attempts` times.
- **You approve `define` and `plan`.** Each phase's `needs_approval` in `config.yaml` says so. Reject with a note and the phase re-runs as a refine round. `build`, `verify`, `review` and `ship` move on by themselves.
- **The agent handles its own problems after `plan`.** A stop goes to a fresh resolver session first, a failing verify gate is debugged inside `verify`, blocking review findings get an automatic fix plan and fix round, and a CI failure gets a fix and a push. You hear about it only when those run out.
- **A usage limit or an outage is a hold, not a stop.** The run shows as `held`, waits, and carries on by itself (section 8).
- The **runner is the only thing that commits and pushes**. Agents never do. A run that reaches `ship` ends with a PR marked ready for review once CI passes. Nothing merges it but you.
- All state is an event log under `<state dir>/runs/<run>/` (the state dir is outside the repository by default; see `paths.state_dir` in section 14). The CLI, the dashboard and the PR body read the same events.

You stay in charge of three things: answering the questions in `define` and `plan`, approving those two phases, and merging the PR.

## 2. Prerequisites

| Need | Check |
|---|---|
| Python 3.12+ and `uv` | `uv --version` (the installed tool and `bin/agentflow` both run on `uv`; PyYAML comes from the package or the script header) |
| `git` with an `origin` remote and the fork branch (`main` here) | `git remote -v`, `git branch --list main` |
| GitHub CLI, signed in (needed by `ship`, `--issue`, and `queue`) | `gh auth status` |
| Claude Code (the default agent) | `claude --version`, and run `claude` once interactively so it is signed in |
| Codex CLI (optional second agent) | `codex --version`, and `codex login` once |
| The repo's skills at `<project.skills_dir>/<name>/SKILL.md` (`.claude/skills` by default; a repository with none runs on the engine's bundled `agentflow-*` skills) | `ls .claude/skills` |
| Everything above in one go | `agentflow doctor` |

A run works in its own worktree, so the main checkout may be on any branch and hold uncommitted work.

Agent runs spend real money, and a run has two budgets. `defaults.run_budget_usd` (25 here) is the soft one: when the run's summed cost crosses it, the runner sends one notification (`budget_soft_reached`) and the run goes on. `defaults.run_budget_hard_usd` (65 by default) is the hard one: crossing it stops the run with `budget_exceeded` for a human's approval. A plain `approve` of that stop sets the hard budget to the spend so far plus one soft budget, and `--budget <usd>` sets it exactly. A feature run's soft budget grows to fit its plan when `build` starts (`defaults.task_budget_usd` per open task), while the hard one never does: if the estimate is above it, you get one notification and the run goes on. A run started before the soft budget existed keeps its one budget, which stops it. The runner checks before each agent call, so a call already running can go past either budget. Claude's cost is what Claude reports, or an estimate from `agents.claude.prices` for a session that ended without a report (a context rollover, a timeout). Codex steps are recorded as 0, so the budget does not count them. The hard budget now defaults to 65, and `validate` refuses a hard budget below the soft one: if you set `run_budget_usd` above 65 (in the pack or the user file), also set `run_budget_hard_usd`, because it must be at least the soft budget.

## 3. One-time setup

Install the engine once as a tool, from a checkout of this repository. This puts an `agentflow` command on your PATH, and it runs from any directory:

```bash
uv tool install --from /path/to/agentflow-harness agentflow     # first install
uv tool install --reinstall --from /path/to/agentflow-harness agentflow   # after pulling engine changes
```

A `git pull` of the checkout does not change the installed tool, and a plain `uv tool install` on an existing install does nothing: after pulling, always reinstall with `--reinstall`. The guided update flow (an agent can run it for you) is "Updating an existing install" in `SETUP.md`.

`pyproject.toml` lists the files under `agentflow/` as `cache-keys`, so uv rebuilds its cached wheel when one changes. If an install still serves stale code, `--reinstall` is the fallback. `bin/agentflow` stays for working on the engine itself: it runs `agentflow/flow.py` straight from the checkout, so an edit takes effect with no reinstall.

Then run these from the repo root of the project you drive.

```bash
# 1. The machine: agent CLIs and logins, gh, origin, Docker, the state dir, each gate's programs.
agentflow doctor

# 2. The config must be valid. It must print "0 warnings".
agentflow validate

# 3. Fast sanity check of everything the runner can see, with no agent calls.
agentflow next

# 4. Optional but recommended (in this repository): run the engine's tests once (25-60 minutes; a loaded machine is slower).
#    --no-project keeps uv from picking up any project file: the engine needs only pyyaml and pytest.
uv run --no-project --with pyyaml --with pytest pytest agentflow/tests --import-mode=prepend -q
```

Then check the three files that decide what agents may do:

- `.agentflow/config.yaml` is the one file with all behaviour: models per phase, gates, conditions, budget, push and PR. **Agents cannot edit it during a run.** Run `agentflow validate` after every edit. It is the repository's pack (section 14), read from the main checkout even when you run `agentflow` inside a run's worktree.
- `.claude/settings.json` (shared) and `.claude/settings.local.json` (yours, git-ignored) hold the tool rules for Claude. The runner passes no `allow` rules of its own, except to a read-only session (`agents.claude.read_only_roles`), which gets a short allow list of reads and read-only `git` (section 14). It passes `--settings` deny rules of its own (the pack's forbidden paths, including `.agentflow/**`, and the state dir's runs root), and headless agents run with `--permission-prompts none`, so any command that would prompt is denied. If a step needs a command, add an `allow` rule for exactly that command.
- The `gates:` and `gate_sets:` in `config.yaml` are the repository's quality bar. Never weaken a gate to get a run through.

A denied command does not stop a run by itself. The runner records a `permission_denied` event on the step, and the agent carries on without the command, usually ending the step as `blocked`. That is the system working. Decide, add the narrow rule, then `agentflow approve <run> <step-key>` to resume the step's session, or `agentflow retry <run> <step-key>` to start it fresh. The exception is a denial in a read-only session (`agents.claude.read_only_roles`, recorded with `read_only: true`): it is by design, so never answer it with a rule.

## 4. Pick the lane

| You want to… | Lane | Command | Ends with |
|---|---|---|---|
| Build a module end to end | `feature` | `agentflow run feature --module crm` | draft PR |
| Write or amend a spec only | `feature`, stopped after define | `agentflow run feature --module crm --to define` | commits on the run's branch, no PR |
| Fix a bug | `bug` | `agentflow run bug --issue 42` (or `--log PATH`, or `--task "…"`) | draft PR |
| Change a prompt, model, chunking or retrieval (a pack with an `eval` lane) | `eval` | `agentflow run eval --task "…"` | draft PR (eval gate must pass) |
| Decide a design question in the idea doc (a pack with a `design` lane) | `design` | `agentflow run design --topic "Clarify thresholds"` | one commit on its own branch, draft PR |

`agentflow` refuses a lane its pack's `lanes:` does not list. Not sure which? `agentflow next` prints the lane, the stage and the next skill for the repo as it stands.

Every command starts with `agentflow`, the tool installed in section 3. When you work on the engine itself, `bin/agentflow` in this checkout runs `agentflow/flow.py` straight from the source, so an edit takes effect with no reinstall. To put that one on your PATH instead (`~/.local/bin` must be on your PATH):

```bash
ln -s "$PWD/bin/agentflow" ~/.local/bin/agentflow
```

## 5. The first run, step by step

Use a small module or a spec-only run for your first time.

**Step 1. Ask what would run, with no agent calls.**

```bash
agentflow explain feature --module crm
```

Each phase and step shows `✓ run`, `– skip (reason)`, `? ask (reason)` or `⏸ <phase>_approved`. A skip reason names the condition that decided it (for example, the spec is already approved). If it says `? ask`, a condition could not be decided from the files. The run will ask you.

**Step 2. Preview the commands.**

```bash
agentflow run feature --module crm --dry-run
```

It prints the agent command per phase and the gate commands, and creates nothing: no run folder, no worktree, no agent call. Check the models and the gates.

**Step 3. Start the run.**

```bash
agentflow run feature --module crm
```

It creates a worktree under the state dir's `worktrees/<run>` (`project.worktrees_dir` in the pack moves it) on `flow/feature/<slug>`, forked from `main`, and starts at the first phase that is not skipped. It stops at the first question or approval. The run id looks like `20261030-0915-feature-crm`.

Useful options: `--from plan --to build` (start and stop at chosen phases; the `--to` phase still raises its approval), `--model plan=sonnet` (one phase's model, this run only; it replaces that phase's whole role map), `--detach` (run in the background, logging to `<state dir>/runs/<run>/runner.log`).

A foreground run outlives its terminal: if the window closes, the runner carries on and writes to the same `runner.log`.

**Step 4. Answer, review, approve.** Every stop lands in the inbox:

```bash
agentflow inbox                       # every run waiting on you, with its questions
agentflow status                      # all runs: phase, step, status, spend
```

For questions, use the exact id the inbox shows (ids are case-sensitive, and agents normally write `q1`). Repeat `--set` per question. The run waits until every question has an answer.

```bash
agentflow answer <run> --set q1="Use the per-process token cache"
```

With no `--set`, `agentflow answer <run>` asks each unanswered question in the terminal. You can also fill the `Answer:` lines in the file `agentflow inbox` names, then run `agentflow answer <run>` to record them: editing the file does not continue the run by itself. A `spec_gap` answer is written into the spec as its own `Decide …` commit, and `--record` does the same for any other answer.

For a phase approval, read the handoff and the diff the inbox shows, then:

```bash
agentflow approve <run> plan          # next phase starts in a fresh session
agentflow reject  <run> plan --note "Split task 3 into two tasks"   # refine round; note is required
```

Rejecting a stop inside one plan task (`build/build/task-2/implement`, `…/review` or `…/commit`) sends only that task back for a refine round; the other tasks keep their commits and start no session. Rejecting the phase still refines every task. In any refine round of `build`, a task whose implementer answers `unchanged` and leaves the tree alone gets no review and no gate run (while the run is in `build`, its card shows `– review task N (unchanged)`).

`approve`, `reject`, `answer` and `retry` record the action and then **continue the run in the foreground**. Add `--detach` to continue in the background, or `--no-continue` to only record. Wherever a command takes `<run>`, any part of the id that matches one run is enough.

On the dashboard, approving `plan` starts `build`, because `build` needs no human. Approving `define` doesn't start `plan`: when the next phase also needs you, the card rests as **ready** in its column, and you choose:

- **Continue → `<phase>`**, or drag the card to that column: the next phase starts. Same as `agentflow resume <run>`.
- **Mark done**, or drag the card to Done: the remaining phases are skipped, `ship` pushes the branch and opens a **draft PR**, and the card moves to Done with a link to the PR. Same as `agentflow resume <run> --mark-done`. The dialog names the phases that won't run, and the PR lists them too.

Cards move one phase at a time. To redo a phase, Reject it before approving. If the push or the PR fails, the card stays out of Done and the reason appears in the dashboard's Inbox; fix it and approve the stop to try again, which never opens a second PR.

**Step 5. Repeat until the last phase.** `build` commits per task (each task: implement, gates, review, one commit). `ship` pushes the branch and opens a **draft PR** to `main`. Review that PR on GitHub as you would any other. Done on the board means this draft PR is open; merging it is still yours.

## 6. Running with Claude and with Codex

### Claude (default)

Nothing to set up beyond section 2. `agents.claude` in `config.yaml` controls it. The models are set per phase (`phases.<phase>.model`), with `agents.claude.models` as the fallback for calls outside a phase's own steps, such as recording a decision. A role map picks different models inside one phase, and needs a `default`:

```yaml
phases:
  build:
    model: {default: sonnet, review: opus, plan: opus}
```

This repository's pack sets these (`agentflow config show --effective phases` prints any pack's):

| Phase | Model in this pack | Engine default |
|---|---|---|
| `define` | opus; sonnet for `apply`, which files answers you already gave | sonnet |
| `plan` | opus | sonnet |
| `build` | sonnet for the implementer and the per-task reviewer; opus for `plan`-role calls (the plan sizer, resolvers) | sonnet |
| `verify` | sonnet | sonnet |
| `review` | sonnet for the reviews and `fix_findings`; opus for `plan_fixes` | the same |
| `ship` | none for `finish` and `ci` themselves; their `sync` and CI `fix` sessions (`role: plan`) use the fallback, `agents.claude.models.plan`: opus | sonnet |

The runner sizes every step before it starts: a short read-only session answers a fixed checklist about the task, and the runner turns the answers into a level within `effort.allowed`. Build tasks and their reviews are sized from the plan by the plan model. Define, plan, review and debug steps never run at `low` and are sized by their own model; other steps by the mechanical model. A step goes up one level once, on its first failed gate or a reopening review, in the same session. `effort.sizing: false` runs every step at `effort.default`, with define, plan, review and debug steps still at `medium` or above. The runner records the level and passes `--effort` on every call, including resumes. A sizer session runs the repository's Claude Code hooks, and a hook that writes into the worktree stops the run with a `sizer_edit` guard violation, as any change a sizer makes does. To get past a `sizer_edit` stop, put the work tree, `HEAD` and the git state back as `sizer_started` recorded them and approve, or cancel the run and run it again. A comparison that cannot be completed stops the run too: sizing fails closed. Project skills load headlessly from `.claude/skills/`. Tool rules come from `.claude/settings*.json`.

With `route.mode` on or `observe`, the runner also triages a run of a lane in `route.lanes` once, before its first phase: a short read-only session on the first phase's `plan` model answers the sizer's six questions about the whole change, plus how many plan tasks and files it expects, and records `route_profile`. The profile comes from a fixed rule in engine code, not from the model: the security overlay, a `risk` flag or 12 tasks or more give `L`; a `mechanical` change with none of the five other questions (`interface`, `risk`, `ambiguity`, `breadth`, `novelty`) answered `yes` or `unsure` (`unsure` counts as `yes`) and at most 2 files gives `XS`; at most 3 tasks with no `interface` or `risk` flag give `S`; anything else is `M`, and an unusable answer falls back to `L`, the full route. The session may propose a profile, and the runner takes it only when it is larger than the rule's pick, never a smaller one. `off` (the default) runs no triage and records nothing; `observe` records the profile with `applied: false` and runs the full route; `on` records it with `applied: true`. A resumed run is not triaged again. A triage that changes the repository stops the run with a `sizer_edit` guard violation on `<first phase>/route`, cleared the same way as a step sizer's: put the work tree, `HEAD` and the git state back and approve, and the run is triaged again before its first phase starts. That check holds even when the pack has since turned `route.mode` off or dropped the lane: a triage that stopped or died before the first phase is compared before that phase runs.

Under `route.mode: on`, the runner applies the run's recorded profile; under `observe` nothing of it applies. A step its `skip` names is recorded as `step_skipped` with condition `route:<P>` and reason `route profile <P> skips it`, decided before the step's `when` (a reconcile step keeps its own reconcile-only check first), and only a top-level `<phase>/<id>` step can match. `doubt_rounds` caps a phase's reconcile rounds, and the refine rounds of a phase that needs no approval, at `min(doubt_rounds[phase], autonomy.finding_rounds)`, never below 1: a profile lowers the cap and never raises it, and once the cap is reached the approval page says the rounds are used up. `per_task_review: false` drops the review of a plan task that the plan sizer did not flag `risk`, outside the security overlay, and records `review_skipped` (`route profile <P>`) once; the task is committed as a small plan's is. A task with no plan-sizer answers (sizing off, or a fallback) keeps its review, and so does a batch whose members include one that keeps it. A profile name the pack no longer defines (a config edit mid-run) applies nothing, so the run takes the full route. `agentflow explain <lane> --profile <P>` shows what a profile would skip: each step in its `skip` reads `skip (route profile <P>)`, whatever `route.mode` is; a name not in `route.profiles` is an error that lists the defined ones.

The route only goes up once the plan is known. Before each phase starts, and again in build once the plan sizer has answered, the runner checks the run's profile against the plan: more than 3 open tasks call for at least `M`, and 12 or more, a task the plan sizer flagged `risk`, or the security overlay call for `L`. A larger profile is recorded as another `route_profile` with `proposed_by: runner`, `upgraded_from` the profile it replaces, `applied` as the run's last record had it, `facts` `{tasks, risk, security}` and a reason (`the plan has 9 tasks`, `a task is flagged risk` or `the security overlay applies`). So a plan that grows after the triage said `S` gets its per-task reviews back before its first task. A smaller profile is never taken, and under `off`, in a dry run or for a run with no profile nothing is checked. Under an applied profile the per-task reviews are tiered: a review runs at `high` only for a task the plan sizer flagged `risk` or whose own files touch the security overlay's paths (`overlays.security.when_paths`), and at `medium` otherwise (clamped to `effort.allowed`, never below the judgement floor); a task with no plan-sizer answers keeps the judgement default, `high`.

### Codex

Codex support is an **adapter only, disabled by default, and not yet exercised against a real Codex session** (the tests use a fake agent). Treat the first Codex run as a pilot on a throwaway task.

1. **Create a Codex profile** named `agentflow` in `~/.codex/config.toml`. The sandbox and approval policy live there, not in agentflow. An example (check the key names against `codex exec --help` for your version):

   ```toml
   [profiles.agentflow]
   sandbox_mode = "workspace-write"
   approval_policy = "never"
   ```

2. **Enable the agent:** set `agents.codex.enabled: true` in `.agentflow/config.yaml`. The rest of the block is ready (`profile: agentflow`, the models, the effort argument). From then on every `agentflow run` needs `codex` on your PATH, even a run that stays on Claude.

3. **Move one phase to Codex.** Start with a phase that is easy to review, such as `review` or `build` on a small module. Add `agent` and replace the phase's `model`, and leave its `steps` as they are:

   ```yaml
   phases:
     review:
       agent: codex
       model: gpt-5-codex   # was {default: opus, build: sonnet}
       steps:
         # unchanged
   ```

   **Always change `model` together with `agent`.** A phase's model wins over `agents.codex.models`, and `agentflow validate` checks only that the phase's agent is enabled. A Claude role map left in place passes `validate`, then sends `-m opus` to Codex. For the same reason, `defaults.agent: codex` puts every phase on Codex only if you also replace every phase's `model`.

4. **Validate and preview, then run.**

   ```bash
   agentflow validate
   agentflow run feature --module crm --from review --dry-run     # the argv shows codex exec … -m gpt-5-codex -c model_reasoning_effort=…
   ```

What differs when Codex is the agent:

| Topic | Claude | Codex |
|---|---|---|
| Skills | loaded natively from `.claude/skills/` | the prompt says to read `.claude/skills/<skill>/SKILL.md`, and `AGENTS.md` at the repo root carries the rules |
| Tool permissions | `.claude/settings*.json` allow, ask, deny | the `agentflow` profile's sandbox. `.claude/settings.json` does **not** apply to Codex |
| Effort | `--effort <level>` | `-c model_reasoning_effort=<level>` |
| Cost in `status` and the budget | recorded, or estimated from `agents.claude.prices` | recorded as 0, so neither budget (`run_budget_usd`, `run_budget_hard_usd`) counts a Codex-heavy run |
| Resume | `--resume <session>` | `codex exec resume <id>`, with the writable folders passed as `-c sandbox_workspace_write.writable_roots=…` (unverified end to end) |
| Security review profile | `--agent security-auditor` | not used |
| Usage limits | waits for the reset time | not detected: a failed call counts as an outage, and it retries until `recovery.give_up_h` |
| Context rollover | a fresh session at `context.rollover_pct`, or once a session has compacted `context.max_compactions` times | none |
| `agentflow attach` | opens the step's session | refused |

The guards still hold for any agent: forbidden paths, `HEAD` moved by an agent fails the step, only the runner commits. Because Codex ignores `.claude/settings.json`, check the `agentflow` profile yourself: it must not allow network or writes outside the work tree that you would not allow for Claude.

## 7. Lane recipes

### Feature (`feature`)

Phases: `define`, `plan`, `build`, `verify`, `review`, `ship`. Work that already exists is skipped with a reason (an existing spec skips the idea questions and the draft; an existing plan with open tasks skips `plan`; a plan with every task ticked skips `build`). Expect approvals at `define` and `plan` only.

The steps below are this repository's pack, which writes its own `phases:`. The engine's default workflow (`agentflow/defaults/config.yaml`) differs: its `define` drafts the spec, grills its open questions and has it doubt-reviewed (`spec_review`), its `plan` has a `plan_review`, and it has no `idea`, `contracts` or `security_review` step.

In this pack, `define` runs `grilling` (only without a spec), `spec-driven-development`, `api-and-interface-design` and the open-questions grilling, each when it is needed. `plan` runs `writing-plans`, which also uses `codebase-design` for a package that doesn't exist yet. That design stays in the plan: a public interface the approved spec doesn't have stops the run with a `spec_gap` question. `build` uses `subagent-driven-development` above 3 tasks and `executing-plans` for 3 or fewer (one shared session, no per-task review). On a security path (the security overlay's `when_paths` and `when_keywords`: here the guards, the agent adapters, config trust, `safeio`, the workspace, the pack and layer loaders, `detect`, `init`, `pack_fix` and the run brief) the plan's approval page offers `/doubt-driven-development`: run it yourself before you approve, or approve to skip. The runner never runs it. The same path adds `security-and-hardening` to every step with the `plan` or `review` role, and a `security_review` step to the `review` phase.

With the engine's default phases, before you approve `define` or `plan`, a fresh reviewer (`spec_review`, `plan_review`) tries to find fault with the spec or the plan. It never sees the author's summary, only the artifact and what it must meet. Each `critical`, `high` or `medium` finding makes the runner open a reconcile round on its own: a fresh session classifies every such finding (`actionable`, `noise`, `trade_off`, `contract_misread` or `human_decision`), edits only the artifact for the actionable ones and the reviewer looks again. A review after the first round is told what changed instead of reading the artifact afresh: its prompt opens with the artifact's diff since the last review started (when that diff exists and is at most 400 lines), then the earlier findings with their dispositions, and its turn cap is half the resolved turn cap: the step's own `max_turns`, else its role's `agents.<name>.max_turns_by_role` entry, else `agents.<name>.max_turns` (no cap when none is set, or when the role's entry is `0`). It is still a fresh session that may read the rest of the artifact for context. When there is no usable diff (no earlier review in this round, a base that can't be read, a deleted, new or unchanged artifact, a longer diff), it gets the full prompt and the earlier findings, with the whole resolved turn cap. A round is not opened again when it would only repeat itself: the artifact did not change, the reviewer disputes an answer, two rounds fixed nothing, or `autonomy.finding_rounds` is used up. The review adds no stop. It adds evidence to the approval you already get. Read the approval page's findings, one line each, as `R<round>-F<n>` with its severity, its disposition and a status (`fixed`, `still open`, `disputed`, `asked a human` and so on). Treat everything marked open, disputed or `unresolved` as yours to decide, and read `low` findings too, since the runner does not act on them. A `spec_review` runs only while the spec is awaiting approval, so an approved spec is not reviewed again. There is no lighter switch: to turn the review off, write your own `phases:` without the four steps (it replaces the engine's whole workflow). This repository's pack does exactly that, so its spec and plan reach you without a doubt review.

### Spec only

`agentflow run feature --module crm --to define` runs the `define` phase and ends after you approve it. Approved from the CLI, it only commits, on the run's worktree branch, and never pushes: you review the commits, then merge or push them yourself. Approved on the dashboard, it rests as ready, and **Mark done** opens its draft PR. It doesn't count as starting the module in `agentflow queue`, and the Board keeps it in the `define` column with the badge `stopped after define`.

### Bug (`bug`)

`define` (the `debug` step) → `build` (`regression_test`, then `fix`) → `verify` → `review` → `ship`. The regression test must **fail first**: if the agent's test command passes before the fix, the run stops with `red_test_passes`. After the fix, the same command must pass in addition to the gates. The command is the agent's text, so agentflow refuses shell syntax (`;`, `|`, `&`, `$`, redirects), runs it as an argument list without a shell, and runs it only if an `allow` rule in the main checkout's `.claude/settings*.json` covers it. If it stops with `blocked`, add the narrow rule or change the command, then approve.

The `eval` and `design` lanes below are not in the engine's defaults or in this repository's pack. The engine's `python` test fixture pack (`agentflow/tests/fixtures/packs/python/.agentflow/config.yaml`) defines them, and they show what a pack can add. Copy its steps, conditions and overlays into your own pack to use them.

### Eval (`eval`)

`build` (the `change` step) → `verify` (the eval gate) → `review` → `ship`. For changes to prompts, models, chunking, embeddings or retrieval. The eval gate must pass. A regression stops the run with `eval_regression`. `eval/baseline.json` is a forbidden path: only a human changes it.

The gate is not only for this lane. A `feature` or `bug` run whose diff touches `overlays.eval.when_paths` runs it in `verify` too, and any run needing it runs it again after `fix_findings`, so a review fix cannot skip it.

### Design (`design`)

Decides open questions in the idea doc. Like every lane it works in its own worktree on `flow/design/<slug>`, so the main checkout can be on any branch and hold any work. Flow: `define` writes questions, you answer, it edits the doc (a Decisions Log row, the Open Questions removal, and an ADR index entry when an ADR is added; checks enforce them), you approve, and `ship` makes one commit (`Decide <topic> in …`, the message the pack's `type: commit` step sets), pushes the branch and opens a draft PR.

## 8. Operating a run

| Goal | Command |
|---|---|
| All runs, phase, step, status, spend | `agentflow status` (live: `agentflow status --watch`) |
| One run in detail | `agentflow status <run>` |
| Agent processes running now (model, effort, context, spend, idle) | `agentflow agents` (live: `agentflow agents --watch`) |
| Board, workflow and agent views in a browser | `agentflow dashboard` (prints a `http://127.0.0.1:<port>/#token=…` URL; port 7788 by default, `--port 0` picks a free one) |
| Everything waiting on you | `agentflow inbox` |
| Continue a paused, `stalled`, `error` or `ready` run | `agentflow resume <run>` (a stop waiting on you stays until you approve, answer or reject it) |
| Finish a `ready` run here and open its draft PR | `agentflow resume <run> --mark-done` |
| Run a step again in a fresh session | `agentflow retry <run> <step-key>` (with no key: the run's failed step, which only a `guard_violation` leaves). On a step of a phase that is already approved, the retry walks that phase again once; on a `conformance_failed` stop it also clears the stop, so `finish` audits again |
| Pause (the running step finishes first) | `agentflow pause <run>` |
| End a run and stop its agents (cannot be undone) | `agentflow cancel <run>` |
| Open the waiting step's Claude session by hand (no runner may be live) | `agentflow attach <run>` (then `agentflow resume <run>`) |

A run started with `--issue N` adds the `issues.in_progress_label` label and one comment to the issue, keeps the label while the run waits, pauses or stops on an error, and removes it when the run ends `done`, `failed` or `cancelled` (or, if GitHub failed then, when the run is archived). Once its draft PR opens, the runner puts it in the issue's Development section, so merging it closes the issue (an epic gets a comment with the PR's link instead). If GitHub fails then, the link is tried again on every CI round and at archive. Every Backlog card that names an issue starts such a run: a synced issue, and a feature or bug card with an issue number. A feature card in the `module_lane` with only an issue works on the module `issue-<N>`, a new spec, or a new row in a capability map.

With `issues.sync_label` set, the dashboard reads the open issues that carry that label every minute and shows each one as a Backlog card (`issue:<N>`, with a link to it), in the lane `issues.lane_labels` picks from its labels, else `issues.sync_lane`. An issue leaves the Backlog when a run here starts on it, and leaves GitHub's list when it is closed or loses the label; it can't be removed by hand. An issue that already carries the in-progress label but has no run on this machine shows **Taken elsewhere**: someone else picked it up, and Start answers 409 until the label comes off. When `gh` fails, the board keeps the last list and says why.

An issue that GitHub marks *blocked by* another issue (the Relationships menu) shows `Runs after:` with its blockers, and its Start is refused until each blocker is met: closed on GitHub with no live or open-PR run here, or its run here merged. The blocking issue shows `Blocks:`. *Parent*, *sub-issue* and *relates to* order nothing. A blocker in another repository holds the issue until it is closed there. When the dependencies can't be read (an old `gh` without the `blockedBy` field, or a list GitHub truncated), the card shows `Dependencies unknown` and Start is refused instead of showing `Ready`; `agentflow doctor` flags a `gh` that lacks the field. Start also asks GitHub again for the issue's blockers at that moment, and a blocker added since the last refresh fails the start with a message on the card. There is no override: to run two issues in parallel, remove the relationship on GitHub. `agentflow run <lane> --issue N` from the CLI is not checked.

**Stops you will meet** and what to do:

| Stop | Meaning | Do |
|---|---|---|
| `<phase>_approved` | `define` or `plan` finished, or findings in a later phase outlasted the fix rounds | read the handoff, diff and findings, then `approve` or `reject --note`. Approving a later phase ships its open findings |
| questions in the inbox | the agent cannot settle something from the docs (`needs_human`) and the runner did not take its recommended answers (a `boundary` question, no single recommended option, a question asked again, or `answer_recommended: false`), or the runner cannot decide a condition (`condition`, a yes or no under the id `answer`) | answer, then the run continues |
| `fix_attempts_exhausted`, `blocked`, `step_timeout`, `max_rollovers` | the runner gave up on the step. A `step_timeout` is a call past `defaults.step_timeout_min`, or, with `watchdog.no_progress_min` above 0 (15 by default), a session whose stream stayed quiet that long (`watchdog_fired`); in a `resolve: true` phase a resolver settles it first | fix the cause, then `approve <run> <step-key>`: the step's session resumes and is still verified and committed. `retry` starts it fresh |
| `blocked_repeat` | a resumed session blocked again with the tree unchanged, so a plain `approve` is refused. When a human already approved this stop (a `blocked` or `blocked_repeat` stop of the same step, not counting the runner's own settling, restarting at `retry`) and it came back, the notification and the inbox item say how many approvals it has outlived (`blocked again for the same reason after N approval(s)`); the count is `times` on `hitl_raised`. The summary is not compared, since it is the agent's prose. The wording reaches a human only when the stop goes to one directly: in a phase without `resolve`, with `autonomy.resolve_kinds.blocked_repeat` at 0, or with no resolve step configured. Under the shipped `blocked_repeat: 2` in a `resolve: true` phase, a resolver's reopened session stops as a plain `blocked`, which carries no count | fix the cause, then `retry <run> <step-key>` for a fresh session, or `approve <run> <step-key> --note "..."` to tell the session what changed |
| `turn_cap`, `budget_cap` | a session reached its role's turn or spend cap (`--max-turns`, `--max-budget-usd`); a review (`role: review`) reached it, so it is not taken as complete (there is no wrap-up for a review); or one wrap-up turn (the same session, `--max-turns 3` and at most $2.50, telling it to write its result now) did not finish an editing step. The inbox lists what the agent said was left to do. In a `resolve: true` phase a resolver looks once first (`autonomy.resolve_kinds`) | raise the cap once: `approve <run> <step-key>` resumes the session, and each call has its own cap. Split the step: `approve <run> <step-key> --note "Finish <part> as done now and stop"`, then add the rest as a new task. Descope: `approve <run> <step-key> --note "Drop <part>: <why>"`. Start over: `retry <run> <step-key>`. To raise a cap for good, set `agents.claude.max_turns_by_role.<role>`, the step's `max_turns` or `agents.claude.session_budget_usd.<role>` (`0` is no cap) |
| `agent_unavailable` | calls kept dying after reaching the model, or an outage outlasted `recovery.give_up_h` | check the step's transcript, then `approve <run> <step-key>`: the step's session resumes |
| `budget_exceeded` | the summed cost crossed the hard budget, `run_budget_hard_usd` (the soft `run_budget_usd` only notifies) | `approve <run> <step-key>` allows the spend so far plus one soft budget; `--budget <usd>` sets the hard budget to a number above the spend so far |
| `guard_violation` | a step touched a forbidden path twice (the runner puts the first back), moved `HEAD` or used a user-only skill | undo the change, then `approve <run> <step-key>`: the runner checks the tree again and restarts the step in a fresh session. Approving does not let the change through |
| `review_unresolved` | blocking review findings remain after the fix round and the resolver | fix by hand if you want, then approve: the reviewer looks once more, then the task commits, with any open finding in the commit body. Only your approval can do that |
| `ci_failed` | CI still fails after `ci.fix_rounds`, reports no checks, or never settles. With `ci.watch_max_h` above 0, checks still pending after `ci.timeout_min` are watched (`held`, reason `ci_pending`, with one notification that nothing is needed) for up to that many hours before they stop | read the logs in the inbox, fix the cause, then `approve <run> ship/ci` for fresh rounds |
| `preflight_failed` (`<first phase>/preflight`) | with `preflight.enabled: true`, the machine cannot run the lane's gates: a program is missing or cannot start, Docker does not answer, or a `setup` gate fails. Raised before any agent runs, so nothing has been spent | fix what the inbox lists, then `approve <run> <phase>/preflight` runs preflight again (`--note` is refused: no agent would read it). A `setup` gate that fails on the base branch itself needs a fix there, or `preflight.enabled: false`. `reject` is refused: there is nothing to refine |
| `environment` (`<step-key>`) | a resolver named the stop's cause `environment`, and the runner's probes of the step's gate programs (and the `setup` set) fail too: this machine cannot run them. One inbox item, notified once per distinct problem (a repeat of the same problem is not notified again until the machine was found fixed or you overrode the check with `approve --note`) | fix the machine. `agentflow queue` and the dashboard check it again every 2 minutes or so and approve the stop themselves (`by: runner`) once the checks pass, then resume the run. `approve <run> <step-key>` checks the machine again first and stops again if it still fails; `approve --note "..."` goes on without the check. `reject` is refused: there is nothing to refine. `cancel` ends the run |
| `red_test_passes`, `eval_regression`, `gate_failed` | a verification step failed | fix the cause, then approve to re-check |
| `max_rounds` (`define/grill_open_questions`) | the spec still has open questions after 2 grilling rounds, or after a round whose grill asked none (the condition and the grill disagree: the summary carries the condition's count, so check how the spec files its answered questions) | `approve` goes on as it is; `reject --note` sends the phase back |
| `dirty_tree` (at `ship`) | uncommitted changes in the worktree | commit or discard them, then approve |

**Holds are not stops.** A usage limit, a usage window governor hold (`run_held` reason `usage window`), an outage, or CI checks still pending after `ci.timeout_min` (with `ci.watch_max_h` above 0, reason `ci_pending`) need nothing from you. The run shows as `held` and notifies you once. It keeps its queue slot, except during a `ci_pending` hold, which frees the slot so `agentflow queue` can start another run while CI is watched. `agentflow status <run>` prints the reason and the time, and the Board's badge reads like `held until 14:30 (usage limit)`.

- A usage limit waits for its reset time, with no cap.
- A usage window hold waits until the window drops below its mark or resets. To end it early, set `usage.governor: off` (in the pack or the user layer: a held run takes it at its next poll) or delete `~/.local/state/agentflow/usage_window.json`.
- An outage retries with a backoff of up to 15 minutes, for `recovery.give_up_h` (24) hours.
- A call that reached the model and still died is retried, but the third such failure (`recovery.failed_attempts`) stops the step, because those calls cost money.

The last two end in an `agent_unavailable` stop. `pause` and `cancel` still work during a hold. If the runner itself dies during a hold, nothing restarts it: run `agentflow resume <run>`.

**Most questions never reach you.** A question's `kind` is `spec_gap`, `ambiguity`, `conflict`, `review_dispute`, `boundary` or `other`, and the agent marks one option of each as recommended. In every phase the runner takes those options itself (`autonomy.answer_recommended`), records them as answered `by: runner`, notifies you with one line, files a `spec_gap` answer in the spec as its own `Decide …` commit, and lists each decision under "Decisions the runner took" in the pull request, so you review them there. A `boundary` question is one the repository's docs reserve for a human (an "ask first" or "never" rule): it is in `autonomy.human_question_kinds`, so it always stops for you, parked or not, and your answer goes in the task's commit body, as an `ambiguity` or `review_dispute` answer does. A question with no single recommended option, or one the step asks again after the runner answered it, also comes to you.

**Parked questions are not stops either.** When a plan task asks a question that later tasks can go on without, the run parks that task and carries on with the tasks that do not depend on it. It stops only when no runnable task remains. `agentflow inbox` lists the task as `parked`, and `agentflow answer <run> --key <step-key>` answers it.

A resolver session may also record what it found. Its result can carry `facts`, short statements that hold for the whole run (for example, a gate that fails for a reason outside the task). The runner keeps each new one as a `run_fact` event, and every later agent session of the run sees them under "What this run already found" in its prompt, so it checks them instead of diagnosing the same thing again.

A resolver may also name the stop's cause in `stop_class`: `environment`, `flaky`, `guard_false_positive`, `spec_gap`, `impact` or `repeated_failure`. The field is advisory: an unknown value is dropped, never a broken result. The runner records each class once per resolver session as a `stop_classified` event, and acts on two of them:

- `flaky`: only when the resolver changed nothing in the tree, the runner reruns each gate that failed in the step's last gate run alone, twice. If every one passes both times, it records one `flaky: <gates> failed in <step>, then passed twice when run alone` fact. The reruns are not evidence: they write no `gate_result`, and the step's own gates still decide when it resumes. The reruns cost real time, and they happen by default, because the engine's resolve prompt asks for `stop_class`: each rerun is the whole gate, so a `flaky` claim on a `verify` gate that runs the full suite runs that suite twice more, tens of minutes for a slow one.
- `environment`: the runner probes the programs of the gates that ran on the step (its fix loop and resolver included), plus the `setup` set, as preflight does (or every gate of the lane when none ran there). When they pass, the step reopens at once as usual: the probes cannot see every fault (a port in use), and the resolver's attempts still bound the loop. When they fail, the resolve is closed and the stop becomes one `environment` inbox item (`environment_waiting`). You are notified once per distinct problem, and again when the problem is back after your `approve --note` override. `approve` checks the machine again first (`environment_rechecked`) and raises the stop again if it still fails, while `approve --note "..."` is your override and skips the check. While `agentflow queue` or the dashboard runs, it checks a waiting `environment` stop again at most every 2 minutes, approves it as the runner once the checks pass, and resumes the run. A run whose worktree is gone is left to you. An `environment` stop is an ordinary wait, so `metrics` charges it to `human`, and it can't be listed in `autonomy.resolve_kinds`.

Every other class is recorded only. When a stop's resolve attempts are used up and it goes to you, the runner also records it once as `repeated_failure`.

Any step's result may carry `code_map`: up to 8 one-line entries naming existing code the step had to search for (`path:line`, signature, use). The runner keeps them as `code_noted` events (the newest 40, deduplicated), and every later session of the run sees them under "Code this run has mapped" in its prompt, so it opens that code at the line given instead of searching for it again.

The runner fixes what a review finds by itself: `plan_fixes` makes the plan, `fix_findings` makes the change and runs its gates, then fresh review sessions check the branch again. If you stop at `review_approved` because findings outlasted those rounds, reject with a note to send it round again. A refine round belongs to its phase: once the runner approves `verify`, `review` starts with no round of its own and reviews the branch. `verify` has no fix plan of its own: it proves the branch works, debugs a failing gate in its own step, and a blocking verify finding re-runs `verify` in a fresh session. The PR's `Verification` section lists what verify proved and what it could not, and marks evidence older than a review fix.

**Gates are not run twice on the same tree.** A gate that already passed in this run on exactly the tree a step is about to gate, with the same command (`run`, `cwd`, `when_exists` and `defaults.env`), is not run again: the step gets the earlier pass, and the run records one `gates_reused` event naming it and the step it came from. A step that changed nothing (a `fix_findings` that declined every finding, a `gates_first` step whose session only read the logs) therefore costs no gate time. A failure, a skip and the `setup` set's gates (they start things) always run again. In a fix attempt, the gates the last attempt failed run first; while one still fails, the others wait for the next attempt (`gates_deferred`), and a step still finishes only once its whole set has passed on its final tree.

**The draft PR can open before review.** With `ci.early_pr_after: <phase>`, the runner pushes the branch and opens the draft PR as soon as that phase is approved, so CI runs while review does; it is a draft only, `finish` still audits the final tree, then pushes it and updates the PR's description instead of opening one, marking it ready still needs that audit and a green CI, and a GitHub failure at that point (`early_pr_failed`) never stops the run, because `finish` then opens the PR as usual.

**The machine stays awake while a runner works.** On macOS the runner holds `caffeinate -i` and on Linux `systemd-inhibit --what=idle:sleep`, both tied to the runner's process, and lets go as soon as the run stops for you or ends. `agentflow doctor` warns when neither exists. Set `AGENTFLOW_NO_KEEPAWAKE=1` to turn it off.

The dashboard's Inbox tab, with a count in the header on every view, lists what waits on you: each card has a title in words, the inbox text (its `agentflow ...` command lines folded under "CLI equivalent"), the facts the resolvers found, a phase approval's artifacts and open findings with a button to read the spec or plan, and what a stopped task holds up. Its forms replace the browser's prompt boxes: a note for a stop (required when it blocked again with nothing changed), a radio group per question that starts on the recommended option, and a request-changes box. Approve asks for a second click within 4 seconds, and runs waiting only on a limit or a lost runner are listed under Watch with no buttons. The Board keeps one line pointing there; `dashboard.inbox_legacy: true` brings the old Needs-human list back. The dashboard's Workflow tab shows every phase with its steps, skills, model and gates, from `config.yaml`, with a badge only on a step that one kind of work runs. To see exactly which steps a run walks, open its Run page. A run whose lane walks `define` or `plan` also has a Spec or Plan tab there: every revision that phase committed, rendered or raw, a diff with the previous revision, and the review findings by round, with a dot on the line each one names. The Board's Backlog column is not a phase: it holds the work source's modules the queue hasn't started (one per spec file with `work_source: {kind: specs}`, one per row with `capability_map`), the cards added on the page and the synced GitHub issues, so they have no run yet. Dragging only works on ready cards. The Plan tab's Tasks mode lists each plan task with its status, tries, review, cost and what a blocked task holds up. The Agents tab lists every agent session the run started, each attempt, resolver and sizer with its model, effort, cost, exit and result, and opens a session's transcript as a conversation of text, folded thinking and tool calls that follows a live session while you are at its bottom. The Activity tab tells the run's whole log as sentences ("Task 9 · implement finished: …", "You approved define"), newest first and filtered to Decisions, Agents, Gates, Commits or Stops, folds agent turns into "Agent active 14 min, 37 tool calls" (a checkbox shows them one by one), pages back to the first event with **Load older**, and shows a line's raw JSON under **Raw**.

Approving a stop **never** lets a failing gate, a passing red test or a forbidden change through. It resumes the step and checks again.

Notifications: a terminal bell and a macOS notification fire when a run needs you, and once when a run goes on hold. A run waiting more than `hitl.remind_after_h` (4) hours is re-notified while `agentflow queue`, `agentflow dashboard` or a `--watch` view is running. Waiting never times out into a decision.

## 9. Unattended runs and the module queue

```bash
agentflow queue --max-parallel 2          # loop, every --interval seconds (30): start modules from the work source as dependencies merge
agentflow queue --once                    # one tick, for cron
agentflow queue --include-specs           # required with work_source specs (this repository's): queue every spec file's module
```

The queue reads the pack's `work_source`: a capability map's rows (`kind: capability_map`, the default), or one module per spec file in `project.docs.specs` that fits `project.docs.spec_file` (`kind: specs`). With `specs` it refuses to start without `--include-specs`, because every spec file is a module, finished or not, and starting them all must be asked for.

A module is done when its plan is fully checked and its PR is merged. A module `issue-<N>` (an issue-backed run's) is also done, as `issue closed`, once issue #N is closed on GitHub and no run of it is live; `agentflow backlog undone` overrides that, as it does origin evidence. The queue starts ready modules in the work source's order, never above `--max-parallel`. A run that is waiting for you, paused or held keeps its slot but does not block the others. The one exception is a run held on `ci_pending` (watching CI checks still pending, `ci.watch_max_h`): it frees its slot while it waits. The queue prints `queue: <module> blocked — <reason>` once per change: an unauthenticated `gh`, a failed, cancelled or crashed run, a start that failed, an unknown dependency, a dependency cycle. Failed and crashed runs are never restarted automatically. Only one `agentflow queue` runs at a time, and its start output goes to `<state dir>/runs/queue.log`.

## 11. Safety model in five lines

1. Agents get one writable folder besides the work tree: `<state dir>/workspaces/<run>/`. The run's events, state, inbox and lock live in `<state dir>/runs/`, outside it, and the runner denies agents any edit there.
2. The runner refuses a step that touches a path in the pack's `guardrails.forbidden_paths` (such as `.claude/**` or the golden test files) or the pack itself (`.agentflow/**`, always), that moves `HEAD`, or that uses a user-only skill. It re-checks before every commit and before the push. A plan task that names such a path (a `Create:` or `Modify:` line) stops `build` before its first task and shows in `explain`: a human makes that change, or the plan drops it.
3. Only the runner pushes, only commits it made, never with `--force`. It never writes `Constraints-Approved-By`.
4. The dashboard listens on `127.0.0.1` only and every request needs the token. Do not paste the dashboard URL into chat or tickets.
5. **Residual risk:** gates such as `uv run pytest` execute code from the work tree, which the agent wrote, with your permissions. The guards catch what that code changes in git, not everything it could do on your machine. Review the diff at every approval, and for risky work run agentflow in a disposable environment.

## 12. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| A run fails on a missing tool or a login, or you are setting up a new machine | `agentflow doctor` checks, in order, each enabled agent's CLI and login (`claude auth status`, `codex login status`), with `agents.claude.user_settings` off what the user's own Claude settings hold that a run skips (`claude user settings`: it reads `$CLAUDE_CONFIG_DIR/settings.json`, or `~/.claude/settings.json`, and runs no command; a warning when it has `env`, `apiKeyHelper` or `permissions`, else the count of enabled plugins and hook events; never a value. A file it can't read, such as a symlinked one, an oversize one or one that isn't a JSON mapping, isn't read at all: the check stays `ok` and asks you to check that file for `env`, `apiKeyHelper` and `permissions` yourself), `gh auth status` (needs the network), with `issues.sync_label` set that this `gh` lists the `blockedBy` issue field (`gh issue fields`), the `origin` remote, Docker (only when a gate runs `docker`), that the state dir is writable, whether a run can keep the machine awake (`keep awake`: `caffeinate` or `systemd-inhibit`, a warning when neither exists), the variables a run does not inherit (`inherited environment`, a warning that names them), and that each gate's programs are on `PATH` (`defaults.env.PATH` when set). It prints `ok`, `warn` or `fail` with a fix for each, and exits 1 on any `fail`. A gate program that `gate_sets.setup` may install is a warning, not a failure. A broken user file is reported as a `user config` failure and the checks go on without it |
| A gate or an agent step fails only inside a run, and passes in your own shell | a variable your shell or IDE loaded from `.env` may have been dropped from the run, or one that leaked in may differ from the pack's. `agentflow doctor` has an `inherited environment` check that names the variables a run drops and the file they match (never their values). To keep one, set it in `defaults.env`. `defaults.env_inherit` (playbook section 14) says what is dropped |
| An agent reports another `node`, `python` or `pnpm` version than your shell, or than the gates | a Claude session's Bash tool is a login shell, and on macOS `path_helper` puts `/usr/local/bin` first. The runner pins the shell's `PATH` to its own through `CLAUDE_ENV_FILE` (the step's `transcripts/<step>.jsonl.env.sh`), so start the runner or the dashboard from a shell whose `PATH` has the version you want first |
| `validate` or `doctor` fails on a key the pack uses right after you pulled the harness (for example `work_source.path: missing`) | the installed engine is older than the checkout. Run `uv tool install --reinstall --from /path/to/agentflow-harness agentflow` (section 3), then `validate` again |
| `agentflow validate` prints warnings or errors | the message names the YAML path (`phases.build.model`, `phases.define.steps[4].when`). Fix that line and re-run |
| `run` says the agent command is not found | the preflight checks the `command` of each enabled agent. Install it or fix `agents.<name>.command` |
| A run shows `held` | a usage limit, the usage window governor (reason `usage window`: set `usage.governor: off` or delete `~/.local/state/agentflow/usage_window.json` to end it), or an outage. It carries on by itself (section 8); `pause` or `cancel` if you don't want it to |
| A run shows `stalled` | the runner died (Ctrl-C, a crash, a reboot). A closed terminal does not cause this. `agentflow resume <run>` first waits for any agent that outlived its runner, up to the step timeout, then picks the step up from its recorded session |
| A run shows `error` | the runner stopped on an unexpected exception (event `runner_error`). Fix the cause, then `agentflow resume <run>` |
| Another runner is already on this run | the run lock refuses a second runner. Wait, or `agentflow status <run>` to see it |
| `approve` says "not awaiting approval" | someone (CLI or dashboard) already approved it, or the target is not the exact key. The message names the key the run waits on, such as `build/build/task-2/implement` |
| A step ends `blocked` and its events show `permission_denied` | a command is not covered by an `allow` rule. Add the narrowest rule to `.claude/settings.json` (or your `settings.local.json`), then `agentflow approve <run> <step-key>`. Not for a read-only session's denials (`read_only: true`, `agents.claude.read_only_roles`): those are by design, and the inbox says so. Never add a rule for them |
| `ship` stops with `dirty_tree` | uncommitted files in the worktree: commit or discard, then approve |
| The queue prints `blocked — could not tell whether … is merged` | `gh` failed. Run `gh auth status` |
| Codex steps show 0 cost | expected. Codex cost is not reported; set a stricter `run_budget_hard_usd` or watch the Codex dashboard |
| A run is stuck and nothing helps | `agentflow status <run>` for the step, the run's `events.jsonl` (read-only) for the timeline, `agentflow attach <run>` to look at the session. Last resort: `agentflow cancel <run>` and start again |

## 13. Using agentflow in another repository

The engine (`agentflow/`) names no project: everything a repository decides is in its pack, the `.agentflow/` directory at the root of its main checkout (section 14). `agentflow init` writes a sparse pack, about 15 lines, and everything it doesn't write comes from the engine defaults and a starter (`python-uv`, `node-pnpm`, `go` or `docs-only`).

1. **Install the engine** as a tool, once per machine (section 3): `uv tool install --from /path/to/agentflow-harness agentflow`.
2. **Run `agentflow init [--starter NAME] [--baseline]`** from the repository, on any branch. It reads the base branch through git, never the working tree (unless the repository has no commit yet), and runs nothing from the repository unless you pass `--baseline`. It:
   - finds the base branch from `origin`, picks the starter from `pyproject.toml`, `package.json` or `go.mod` (`--starter` overrides it), and proposes gates: from the CI workflow steps first (`.github/workflows/*.yml`), then `package.json` scripts, `pyproject.toml` tool sections and `Makefile` targets, else the starter's. A step it can't run the way CI does (an action, an install, a matrix value) is skipped with a note.
   - finds `docs/plans`, ADR and spec folders, the repository's own skills and its `CLAUDE.md`/`AGENTS.md`;
   - when it found a top-level `specs/`, `docs/specs`, `docs/rfcs` or `docs/proposals` folder, also writes a fixed `work_source: {kind: specs}` block and a `dashboard.backlog` block (`module_lane: feature`, plus the New task form's fields), so the Backlog lists one module per spec file in `project.docs.specs` and a new feature card writes a new spec, or, given only an issue number, works on that issue as the module `issue-<N>`. When most files in that folder are named `PREFIX-<module>.md` (a short letters-and-digits prefix, at least two files, more than the plain `<module>.md` ones), it also writes `project.docs.spec_file: "PREFIX-{module}.md"`, so those files are modules and not "Not modules". Without such a folder the pack has neither key. The two blocks are fixed data: nothing from the repository is copied into them. The one piece of repository text in the pack is that prefix, and only a word of up to 16 letters and digits is taken;
   - runs `doctor` (step 6) and prints its table;
   - with `--baseline` only: runs each proposed gate once on the base branch in a throwaway worktree in the state dir, and prints a table (gate, command, pass/fail/error, seconds, note). A gate that fails there is written with `baseline: red`, so a run isn't blamed for it, and it leaves the gate sets (if every verify gate is red, they stay, and `init` says runs can't pass verify until you fix them). A missing tool, a timeout or a failed setup is an `error`, never red;
   - writes `.agentflow/config.yaml` once, with `gates_confirmed: false` and `agents.claude.permission_mode: bypassPermissions` (with a comment saying what it allows), and nothing else in the repository.

   It refuses when the repository already has a pack: edit it, or `rm -rf .agentflow` to start over.
3. **Read the notes and the gate table.** The gates are a proposal, and the quality bar is yours to decide: fix the commands, add the gates CI doesn't show, and fix or delete a red gate. `agentflow config show --effective gates` shows the gates together with the starter's.
4. **If you use the bug lane** (on by default), add the `Bash(...)` rule `init` printed to `permissions.allow` in `.claude/settings.json` (shared) or your git-ignored `.claude/settings.local.json`. The bug lane's red/green check runs the regression test only when an allow rule covers it, and `validate` warns until one does.
5. **Set `gates_confirmed: true`** in the pack. `validate` warns until you do.
6. **Check:** `agentflow doctor` (agent CLIs and logins, `gh`, `origin`, Docker, the state dir, each gate's programs), `agentflow validate` (it must print 0 warnings), `agentflow explain feature --module <id>`, and `agentflow run feature --module <id> --dry-run`. Then commit the pack in a PR of its own, so the team reviews the gates and the permission line.

Prompts: put any prompt you want worded differently in `.agentflow/prompts/<name>.md`; it replaces the engine's file of the same name. The engine's `task_inline`, `fix`, `ci_fix`, `fix_findings` and `sync_conflicts` prompts tell a session the runner runs the build or verify gates after it, which holds for every engine default step that uses them, so a pack that puts one of these prompts on a step with no gates gets a session that skips the gates: give such a step its own prompt or a gate set. Skills: a step's skill text is its brief, read from the repository's `project.skills_dir` first and the engine's bundled `agentflow-*` skills second; map your own skills per stage in `skills.map` (section 14). A repository with no skills dir runs on the bundled ones.

After upgrading the engine, run `agentflow validate`: a prompt override that still holds text the engine retired, or that copies an engine prompt unchanged, is a warning, and `agentflow validate --fix --dry-run` shows what `--fix` would change.

Runs, workspaces and worktrees live in the state dir, outside the repository unless `paths.state_dir` puts them inside it; then add that directory to `.gitignore` (`agentflow validate` warns until you do). Removing agentflow from a repository is `rm -rf .agentflow`.

## 14. Pack reference

The pack is the repository's `.agentflow/` directory in the main checkout: `config.yaml`, and `prompts/` for any prompt that replaces the engine's file of the same name. `agentflow` never reads a linked worktree's copy. The engine adds `.agentflow/**` to every pack's forbidden paths and refuses a pack without a non-empty `gate_sets.verify`. One line per key: name, meaning, and whether the Settings page may change it.

**Layers.** `config.yaml` is read over the engine defaults (`agentflow/defaults/config.yaml`), and under your own user file (`$XDG_CONFIG_HOME/agentflow/config.yaml`, else `~/.config/agentflow/config.yaml`), bottom-up: engine defaults, then the starter the pack names (if any), then the pack, then the user file. Mappings merge key by key. A list or a value replaces the one below it, and each entry of `gates` and `conditions`, `record_step` and `resolve_step` is replaced whole. `null` deletes a key from every layer below, and `version` and `engine` are read from the pack file alone. So a pack states only what differs from the defaults, and every key the defaults supply is optional in it. The defaults file carries the minimum pack's values for the keys the code has no fallback for (`effort.default`, `effort.allowed` and the required `context.*` keys: `autocompact_pct`, `rollover_pct`, `max_rollovers`, `progress_file` and `gate_output_lines`), and the engine's own fallback for the other optional ones:
- In `project`: `base_branch` and `fork_from` (`main`), `branch` (`flow/{lane}/{slug}`), `skills_dir` (`.claude/skills`), `agent_rules` (`[CLAUDE.md]`), `commit_trailer` (empty) and `docs` (`specs: docs`, `plans: docs/plans`). There is no default `worktrees_dir`: without one a run's worktree is in the state dir's `worktrees/`.
- In `agents`: `claude` (its command, arguments, models, `effort_arg`, prices, `skill_loading`, `cache_ttl`, `lean`, `user_settings`, `read_only_roles`, the per-role turn and spend caps and `bash_output_chars`, with no `permission_mode` and no `max_turns`) and a disabled `codex`. A pack states `agents.claude.permission_mode` itself.
- In `defaults`, `recovery`, `preflight`, `watchdog`, `usage`, `effort`, `context`, `memory` and `issues`: every key (no `defaults.env`), at the value the engine falls back to where it has a fallback and at the minimum pack's value where it has none, and `defaults.agent: claude`.
- `policy`: `enforce: report` and the four engine obligations (`verified`, `reviewed`, `plan_approved`, `red_then_green`).
- `guardrails` (empty lists), `hitl` (empty: no notification and no reminder) and `dashboard` (`127.0.0.1`, port 7788). `gates` and `gate_sets` are empty: a pack names its own gates.
- **The workflow:** `lanes` (`feature`, `bug`), `phases`, `conditions`, `record_step`, `resolve_step`, `phase_approval`, `checkpoints`, `autonomy`, `ci`, `skills` and `route`. Every step's skill is a `@skills.map.<key>` reference to one of the bundled skills, and its text is the step's brief. A pack that writes `phases:` with `steps` writes the whole workflow, and every one of these keys from the defaults is dropped: the pack states the ones it wants. A pack that writes only a phase's `needs_approval`, `resolve`, `model` or `agent` adjusts the defaults' workflow. `retro_step` is not a workflow key, so the defaults' one stays either way.

The user file holds personal settings only: `agents.<name>.models` for an agent a lower layer defines, `agents.claude.user_settings`, `defaults.run_budget_usd`, `defaults.run_budget_hard_usd`, `defaults.task_budget_usd`, `hitl.notify`, `hitl.remind_after_h`, `dashboard.port` and the five usage-window keys (`usage.governor`, `usage.five_hour_soft`, `usage.five_hour_hard`, `usage.seven_day_soft`, `usage.finish_first`). Any other key, a key that is not text, or a file that is not a mapping is an error naming the file and the key. Nothing in it can set a command, a gate, a guardrail or the workflow.

`agentflow config show --effective [PREFIX]` prints every value with the layer it came from. The Settings page shows the same values, marks one that is not the pack's with `from engine`, `from starter:<name>` or `from user`, and saves into the pack only what the pack must state: for a mapping, the entries that differ from the layers below it or that the pack already states (an inherited entry is removed with `<name>: null` in the YAML tab). A value your user file sets is read-only on the page, so a personal value never lands in the committed pack.

A live run sees a change to any layer file between its phases: the runner takes the new config when it loads, validates and keeps the phases, and records `config_reload_skipped` with the reason when it does not (a broken user file is skipped like a broken pack). `run_options` records the digest of the layer files at the start (`layers_sha256`, and each file's own in `layer_digests`). On `resume`, if any of them changed since, one line names the files, and the run goes on with the files as they are now: `config_trust` still decides which pack file is trusted, by its own hash. The trade-off: an engine upgrade that changes the default workflow is reported on resume, not refused. A run started before this record existed reports nothing.

- `version`: the pack format, `2`. The engine reads format 2 only and refuses any other. Protected.
- `engine`: the engine versions that may run the pack, comma-separated clauses of `>=`, `>`, `<=`, `<`, `==` on dotted numbers, such as `">=3,<4"`. A range that leaves this engine out is refused. Protected.
- `starter`: `python-uv`, `node-pnpm`, `go` or `docs-only`; absent or `null` means none. It names a layer the engine ships (`agentflow/starters/<name>/config.yaml`) between the engine defaults and the pack: it supplies `gates` and `gate_sets.setup`, `build` and `verify` for that kind of repository, and nothing of the workflow, so the lanes stay the defaults. The pack overrides it key by key, as it does the engine defaults: a `gates.<name>` it states replaces the starter's whole, and a `gate_sets` list it states replaces the starter's list. Any other value, a path included, is refused, and the error lists the names. `docs-only` has one gate, `whitespace`, which runs `git diff --check` of every tracked file against the empty tree with `blank-at-eol` off, so a Markdown line break is not flagged. Git's other defaults still apply to every tracked file: `blank-at-eof` and `space-before-tab` flag a file that ends in a blank line, or a space before a tab in the indent, so a repository with such a file fails `build` and `verify` on adoption until the file is fixed. The gate doesn't see untracked files, and a docs repository should add a real gate, such as a Markdown linter. Protected.
- `project`: branches (`base_branch`, `fork_from`, `branch`), `worktrees_dir`, the `docs` paths and the `commit_trailer`. Protected.
- `project.worktrees_dir`: where a run's worktree is made. Unset (the default): the state dir's `worktrees/`, outside the repository. Set: a directory relative to the repository root, without `..` (an absolute path or one that leaves the repository is a `validate` error). Protected, as `project` is.
- `project.skills_dir`: the directory holding `<skill>/SKILL.md` for every skill a step names, relative to the repository root and without `..`; default `.claude/skills`. A skill name is a directory name (letters, digits, `.`, `_`, `:` and `-`, not starting with `-`), never a path. A name found in no `skills_dir` falls back to the engine's bundled `agentflow-define`, `agentflow-plan`, `agentflow-build`, `agentflow-debug`, `agentflow-verify`, `agentflow-review`, `agentflow-respond`, `agentflow-doubt` and `agentflow-retro`, so a repository's own skill of the same name wins. Protected.
- `project.agent_rules`: the files the run brief carries as the repository's rules, as paths relative to the repository root, read from the run's fork commit (never the working tree); default `[CLAUDE.md]`. A path is refused when it is empty, absolute, has a `..` segment, starts with `-`, or sits under `.agentflow` or `.git`. A listed file the commit does not have (other than the default `CLAUDE.md`) is a warning, and the brief leaves it out but still carries the rest. A file over 200000 bytes, a symlink to a refused path, or an object that fails verification is a warning too, and the brief then leaves the rules out, so Claude loads its own memory files. Protected.
- `project.docs`: `specs` and `plans` (directories) are required; `idea`, `decisions` and `glossary` are optional, and a step with `checks:` needs `idea` and `decisions`. `{idea}` is empty when `idea` is unset. `agentflow next` reads uncommitted changes under only these three as a design-doc change. The module list is not here: see `work_source`. Protected.
- `project.docs.spec_file`: a module's spec file name inside `docs.specs`, with `{module}` in it and no other placeholder (write a literal brace as `{{` or `}}`); default `{module}.md`. `agentflow next` reads every file in `docs.specs` that fits it as a module's spec. Protected.
- `project.docs.done_status`: a regex that marks a module done ("spec says done") when it matches a line of its spec's header on `origin/<fork_from>`; default `^[-*>\s]*Status[\s:*]+(done|shipped|implemented)(?![\w-])`. Only header lines count (those before the first `## ` heading, outside code fences; a line longer than 512 characters never counts), matched case-insensitively, so `Status: done`, `**Status:** done`, `**Status: shipped** 2026-01-02`, `- **Status:** done` and `> Status: done` count and `Status: done-ish` or `Status: not done` do not. The spec is read from `refs/remotes/origin/<fork_from>`, never the work tree, so unmerged work never counts. A veto (`agentflow backlog undone <module>`) overrides it. A pattern that does not compile is a `validate` error. Protected, as `project` is.
- `paths.state_dir`: where runs (`runs/`) and agent workspaces (`workspaces/`) live; `~` is expanded and a relative path is relative to the main checkout. Default `${XDG_STATE_HOME:-~/.local/state}/agentflow/<repo-id>`, outside the repository (`<repo-id>` is the checkout's name and a hash of its path). A state dir inside the repository that git does not ignore is a `validate` warning. Protected.
- `work_source`: where the modules `agentflow queue`, the Backlog and the `modules_done` check walk come from. Optional: without it `{capability_map}` is empty, `agentflow next` skips the module order, the Backlog shows only the cards added on the page, and `agentflow queue` refuses to run. Protected. Two kinds, by `kind`:
  - `capability_map` takes `path` (relative to the repository root): a Markdown table with `Module id` and `Depends on` columns, one row per module in build order; `{capability_map}` is its path.
  - `specs` takes no `path`: the directory is `project.docs.specs`, and each file there whose name fits `project.docs.spec_file` is one module. Its dependencies come from the `Depends on:` lines before the spec's first `## ` heading (`**Depends on:** a, b`, `- Depends on: a`), with the bullets or comma list that follow one ending in `,` or nothing; only `none`, `none.` or `none (…)` means none, and an unknown dependency blocks. A `Depends on:` with no value blocks too, as does a spec over 8 KB with no `## ` heading in its first 8 KB, since its header may go on past what is read. Under the bare `{module}.md`, `index`, `readme`, `template` and `changelog` are not modules. A name that is not a lowercase slug, a symlink, a directory and an unreadable file are skipped and shown on the Backlog. `{capability_map}` is empty, a new module is a new spec (no row is written), and `agentflow queue` needs `--include-specs`. `validate` reports a `path`, a `project.docs.specs` that is not a directory inside the repository, and a missing `dashboard.backlog.module_lane`.
- `skills`: `skills.map` names the skill `agentflow next` suggests for each kind of next step: `decide`, `define`, `design_doc`, `plan`, `build`, `build_small`, `verify`, `ship`, `review`, `debug`, `review_feedback` and `doubt`. Another key is an error. `review` and `debug` name the skill for a review and for a bug fix, `review_feedback` the skill sent with blocking per-task findings, and `doubt` the skill of the adversarial review before a human approves a spec or a plan. Each must be a skill in `project.skills_dir` or one of the engine's bundled skills (a name that is not a skill name is an error). Optional: a step with no entry is named by its stage (`Build stage`). Protected.
- `agents.<name>`: the command line and arguments of an agent CLI, its models, `max_turns` and prices. Protected, except `enabled`, `models`, `max_turns`, `prices` and, on the `claude` agent, `cache_ttl`, `lean`, `user_settings`, `read_only_roles`, `max_turns_by_role`, `session_budget_usd` and `bash_output_chars`. The cache and session keys need Claude Code 2.1.327 or later.
- `agents.<name>.command`, `base_args`, `permission_mode`, `effort_arg`, `skill_loading` and `profile`: the agent's argv (`[claude]` with `[-p, --output-format, stream-json, --verbose]`; `[codex]` with `[exec, --json]` in this pack), its `--permission-mode` (one of `default`, `acceptEdits`, `plan`, `dontAsk`, `auto` or `bypassPermissions`; unset in the defaults, `bypassPermissions` from `agentflow init`; a read-only role's call always gets `dontAsk`), the arguments that pass the step's effort (`{effort}` is the level), how a session finds its skill (`native`, the default, or `read_file`, which tells it to read `<skills_dir>/<skill>/SKILL.md`, as Codex needs) and, for Codex, the `config.toml` profile that holds its sandbox. `validate` refuses the permission flags and the flags the runner sets itself (`--setting-sources`, `--max-turns`, `--max-budget-usd`) in `command`'s arguments, `base_args` and `effort_arg`, and, while `read_only_roles` is not empty, `--tools`, `--settings`, `--agents`, `--agent` and `--plugin-dir` in the first two. It also refuses a `permission_mode` outside the list above and an `effort_arg` without `{effort}`. Protected.
- `agents.<name>.models`: the model for each role (`plan`, `build`, `mechanical`, `review`, `debug`, and any a pack adds) when the phase sets none; the engine's are all `sonnet` but `mechanical: haiku`. Not protected; the user file may set it.
- `agents.<name>.max_turns`: the turn cap (`--max-turns`) of a call for a role that `max_turns_by_role` does not name, and for a pack's own roles; unset means no cap there. The role map supersedes it for the roles the map names (`review`, `plan`, `build`, `debug` and `mechanical` by default), so a pack that set `max_turns` now gets the role caps for those. Not protected.
- `agents.claude.cache_ttl`: the prompt-cache lifetime of a run's Claude sessions, `5m` by default; `1h` or `cli` (the CLI's own choice) are the others, and anything else is a `validate` error. Only the claude agent reads it: on another agent `validate` warns. Not protected. When a call's cache writes land in the other lifetime (1-hour writes under `5m`, or only 5-minute writes under `1h`), the runner records one `cli_setting_ignored` event with `setting: cache_ttl` per run and goes on: the CLI did not honour the setting, so check the Claude Code version and the inherited environment. Unless it is `cli`, the runner sets the TTL variable itself and drops the others from both the inherited environment and the pack's `defaults.env`, but it can't override the project's `.claude/settings.json` `env`, which a run still loads: a TTL variable set there wins, and the `cli_setting_ignored` note is how you see it.
- `agents.claude.lean`: `true` by default. A run's Claude sessions then skip the project's MCP servers and user-level state. `validate` warns when it is true and the repository root has a `.mcp.json`, which lean runs don't load: name its servers with `--mcp-config` in `agents.claude.base_args`, or set `lean: false`. Only the claude agent reads it. Not protected. When a lean call still reports auto-memory on, the runner records one `cli_setting_ignored` event with `setting: auto_memory` per run and goes on: the CLI did not honour the setting.
- `agents.claude.user_settings`: `false` by default. When false, a run loads only the project's settings and agents, so `validate` warns when `overlays.security.review_agent` names an agent with no `.claude/agents/<name>.md` in the repository. Set it true to let a run read your own settings and agents. Only the claude agent reads it. Not protected; the user file may set it. The runner passes `--setting-sources` from it, so `validate` refuses that flag in `agents.<name>.base_args`.
- `agents.claude.read_only_roles`: `[review]` by default, a list of roles from the agent's `models` map. A Claude session for one of these roles gets `--permission-mode dontAsk`, the five tools `Read`, `Grep`, `Glob`, `Bash` and `Write`, read-only `git` commands, writes only in the run's workspace `out/` folder (where its result file goes: never `progress.md`, which the later steps that edit the code read), no MCP servers and no skills listing. Real `dontAsk` also runs the CLI's built-in read-only shell commands (`ls`, `cat`, `grep` and the like, and `timeout` or `nice` in front of an allowed command) with no allow rule, so "other commands are denied" means tests, builds, writes and commands that are neither built-in reads nor listed: a probe with Claude Code 2.1.328 denied `find -delete`, `find -exec`, `sed -i`, `sort -o`, `xargs`, `env`, `&`, a newline, `$(...)`, backticks, `<(...)`, `2>`, `&>`, `>|`, `| tee`, `--output` and an environment-variable prefix. Its first prompt carries a note that it is read-only (it must not stop `blocked` for a denial) and a table of the run's gate results so far (each gate's newest, at most 20), so it has no reason to run tests; a pack prompt may place both with `{read_only_note}`, which is empty for every other session, and the engine appends it to a template that has no slot. `guards` fail a step whose session changed the tree (`read_only_edit`: the stop quotes at most 15 paths, the event keeps them all), also when a later session of the step is no longer read-only (a rollover after a config edit, a restarted runner), and refuse a retry of that step until those paths are reverted. The refusal covers only the same step key: a `reject`, a `skip` or a reconcile round reopens another step, whose start adopts the reviewer's edits as its baseline, so revert the paths the stop names first. This is a cost and independence control, not a sandbox. What can widen a read-only session: under `--setting-sources project,local`, the project's `.claude/settings.json` and `settings.local.json` (a worktree copy an earlier step of the run wrote included) and their hooks (a `PreToolUse` hook can allow a call); with `user_settings: true`, your own rules; the agent definition passed with `--agent` (the security overlay's review agent, read from the work tree's `.claude/agents/`; in the 2.1.328 probe its `permissionMode`, `tools` and hooks did not widen the call, unverified for other versions); and `sandbox.enabled` in a project settings file, whose `autoAllowBashIfSandboxed` may auto-allow Bash (the 2.1.328 probe on macOS still denied `touch`; unverified elsewhere). This repository's file allows its `pytest` command. The runner's own allow list holds no test, build or write command, the prompt asks the reviewer not to run them, and the guard catches tracked and untracked edits to the tree. The guard covers only the work tree: it does not see ignored files, `.git/config` or hooks (the same coverage a build step has), writes or deletes outside the work tree by a command a project rule allows (a test command whose options name an output path, such as `--basetemp` or `--junitxml` pointing at the run's state dir), or new files an agent hides with an untracked `.gitignore` or an edit to `.git/info/exclude`. A workspace path with one of `*?[]{}\()!#|@+,`, or a control or whitespace character other than a plain space, makes the step run as today, not read-only, with one `read_only_skipped` note per run. Denials in a read-only session are by design: they are recorded with `read_only: true`, left out of `permission_denied:<tool>`, marked by design in the retro digest and never answered with a `settings.local.json` rule. `validate` errors on a role that is not in `models`, on a step of that agent that has the role and edits the tree (`commit`, `reconciles`, `fix_loop`, `output`, `expect` or `gates`), and on `--tools`, `--settings`, `--agents`, `--agent` or `--plugin-dir` in `agents.<name>.base_args` or in `agents.<name>.command`'s arguments while the list is not empty, because the runner sets them for these calls. On another agent it warns that it has no effect: Codex is unchanged. Not protected.
- `agents.claude.max_turns_by_role`: `{review: 45, plan: 60, build: 60, debug: 60, mechanical: 15}` by default, the `--max-turns` of each Claude call by its role, in the CLI's own unit (a probe found it counts assistant API calls: one message with several parallel tool calls is one turn, so these are not the `num_turns` a result reports). Each call gets its own cap: approving a stop that a cap caused resumes the session with a fresh one. `0` on a role means no cap for it, with no fallback to `max_turns`; `null` on a role removes that entry, so the role falls back to `max_turns`; `null` on the whole key removes every entry; `{}` changes nothing (an empty mapping merges as nothing). A role the map doesn't name uses `max_turns`. A step's `max_turns` overrides all of it, and a doubt review after the first round gets half the resolved cap. `validate` wants a whole number of 0 or more for each entry and a role that is in `agents.<name>.models`, and warns when a non-claude agent sets the key: only the claude agent's calls are capped. Not protected. Upgrade impact: a pack that sets `max_turns` now gets these role caps, so a step may stop at a cap it did not hit before (set the role to `0` or raise it to keep the old behaviour), and a pack that removes a role from `models` (for example `models: {mechanical: null}`) must also set `max_turns_by_role.<role>: null`, because the engine's map still names it and `validate` errors on a role not in `models`.
- `agents.claude.session_budget_usd`: `{review: 4, plan: 10, build: 10, debug: 10}` by default, the `--max-budget-usd` of each Claude call by its role, passed in fixed notation (`4.00`). It counts list-price dollars per call, on a subscription too, and the CLI stops after the turn that crosses it, so a call can overshoot by one turn. It bounds one call, not a step: a reminder, a hold, an approval or a reopen each start a call with a fresh cap, so `defaults.run_budget_hard_usd` is what bounds a step's total and the run. `0` on a role means no cap, `null` on a role removes its entry, and a role with no entry has no spend cap (`mechanical` has none by default); the sizers and the route triage get none. `validate` wants `0` or a number from 0.01 to 1000 for each entry, and a role in `models`; on a non-claude agent it warns. The two maps are independent. Not protected. Upgrade impact: a pack that removes a role from `models` must also set `session_budget_usd.<role>: null` (the engine's map names `review`, `plan`, `build` and `debug`), or `validate` errors on a role not in `models`.

A project `.claude/settings*.json` `env` block can still set the variable; the effect is only cost. `0` leaves it to the environment. `validate` wants `0` or a whole number from 1000 to 1000000, and warns on a non-claude agent. Not protected.

Not protected.
- `defaults.env`: variables set for every agent session and gate of a run, over the inherited environment; none by default. Protected.
- `defaults.run_budget_usd`: the soft budget in USD, 25 by default, recorded when a run starts (`soft_budget_usd`). Crossing it sends one notification (`budget_soft_reached`, once per soft value) and never stops the run. A plain approve of a `budget_exceeded` stop adds this much to the spend so far as the new hard budget. A finite number above 0, or `validate` refuses it. If you set it above 65, also set `run_budget_hard_usd`, because that must be at least this. Not protected; the user file may set it.
- `defaults.run_budget_hard_usd`: the hard budget in USD, 65 by default, recorded when a run starts (`budget_usd`). Crossing it stops the run with `budget_exceeded` for a human's approval; it is the only budget stop. A finite number above 0 and at least `run_budget_usd`, or `validate` refuses it (so a `run_budget_usd` above this default needs its own `run_budget_hard_usd`). Plan sizing never raises it. Not protected; the user file may set it.
- `defaults.task_budget_usd`: USD per open plan task, 2 by default; 0 turns sizing off. When a feature run's `build` starts, the soft budget grows once to the spend so far plus this for each unticked task plus a quarter of `run_budget_usd` (`budget_scaled`, with `soft: true`). It never lowers a budget, never raises the hard one, and a budget a human set is kept; an estimate above the hard budget sends one notification (`budget_estimate_over_hard`) and the run goes on. Negative is a `validate` error. Not protected; the user file may set it.
- `defaults.env_inherit`: which variables of the process that started agentflow a run's agent sessions and gates do not inherit. `drop` is a list of variable names or `fnmatch` globs (`*_URL`), empty by default. `drop_dotenv` is a list of repository-relative files, `[".env"]` by default, with no leading `/` and no `..`: a variable with the same name **and** the same value as a line of such a file in the main checkout was almost certainly loaded by an IDE or shell and is dropped, while one with another value is kept because you set it on purpose. `validate` refuses a bad glob or path. `defaults.env` always wins over a drop, and `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*` and `TERM` are never dropped. The dotenv files are read without following a symlink, up to 256 KB. A run records the dropped names (never a value) as an `env_dropped` event, again only when the set changes on a resume. Protected, so the Settings page and the user file cannot change it.
- `recovery`: how long an outage may last and how many failed attempts a step gets: `give_up_h` (24 hours of an outage, then `agent_unavailable`) and `failed_attempts` (3 calls that reached the model and still died, then `agent_unavailable`). A usage limit is never counted: it waits for its reset. Not protected.
- `preflight.enabled`: `false` by default. `true` makes a run check, once before its first phase: the programs of every gate its lane names (each found on `PATH`, and able to start `--version` in the gates' environment); Docker, when a gate runs it; and the `setup` gate set on the base tree. A failure is one `preflight_failed` stop before any agent runs. A pass is cached for the day by the programs' paths and versions. Gates are skipped as a run would skip them (`when_exists`, a missing `cwd`); `when` and `skip_if` conditions aren't evaluated. `validate` wants a bool and refuses any other key under `preflight`. Not protected.
- `watchdog.no_progress_min`: `15` by default (since engine 3.0; `0` turns it off), and a finite number of minutes up to 1440 (a day). A session that writes nothing to its stream for this many minutes is ended and stopped as `step_timeout`, which a resolver may settle. While the agent waits on a tool call, the limit is `defaults.gate_timeout_min` instead; for Codex, whose stream doesn't show open tool calls, it is always that. One long generation also writes nothing until it ends, so keep the value well above the longest thinking turn (15 is a safe start). Not protected.
- `watchdog.read_only_idle_min`: `5` by default, and `0` or a finite number of minutes up to 1440. A read-only session (`agents.claude.read_only_roles`) with no tool call open ends after `min(no_progress_min, read_only_idle_min)` minutes of a quiet stream and stops as `step_timeout`. While a tool call is open it keeps the limit above, `defaults.gate_timeout_min`, because a read-only reviewer may run a long command. `no_progress_min: 0` switches every watchdog off, `read_only_idle_min: 0` gives read-only sessions the limits above, and `validate` warns when it is above a non-zero `no_progress_min`, where it has no effect. Not protected.
- `usage.governor`: `"on"` by default, `"observe"` or `"off"`. `"on"` holds new work while the plan's usage window is spent (the marks below), `"observe"` only records what it would have held, and `"off"` does nothing. Quote it: YAML reads a bare `off` or `on` as a boolean, which loads as that mode but draws a `validate` warning. A personal key (your user file may hold it). Not protected.
- `usage.five_hour_soft`: `0.75` by default, a fraction above 0 and below `five_hour_hard`, of the 5-hour window. Above it no new run and no new phase starts; sessions already running finish. It is your headroom for work you start by hand. A personal key. Not protected.
- `usage.five_hour_hard`: `0.92` by default, a fraction above 0 and at most 1, of the 5-hour window. Above it no new session starts, not even one inside a running phase. A personal key. Not protected.
- `usage.seven_day_soft`: `0.85` by default, a fraction above 0 and at most 1, of the 7-day window. Above it no new run and no new phase starts. A personal key. Not protected.
- `usage.finish_first`: `true` by default. Runs the governor held go again closest to `finish` first, so a nearly done run gets the first of the freed window; `false` goes oldest first. A personal key. Not protected.
- `effort`: `sizing` (default `true`: the runner sizes each step before it starts; harness proposal §6b), `default` (the level when sizing is off or fails), and `allowed` (the levels a step may run at; it must hold one at or above `medium`, because define, plan, review and debug steps never run at `low`). The step ids `size` and `size-<n>` are reserved for the sizer's own sessions, and `validate` refuses them in a pack. Not protected.
- `context`: auto-compact, rollover and the context window. Not protected, except `context.autocompact_env` and `context.progress_file`. `autocompact_pct` (60) is read by Claude Code against `context_window_tokens` (200000), which the runner passes as `CLAUDE_CODE_AUTO_COMPACT_WINDOW`: without that cap the models' own 1M window makes "60%" 600k tokens, and nothing compacts before the runner's `rollover_pct` (80, of the same window) ends the session. `validate` wants a number from 100000 to 1000000 or `auto` (no cap, Claude's own window), `rollover_pct` above `autocompact_pct`, and `max_compactions` (3) of at least 1. After `max_compactions` compactions the runner replaces the session with a fresh one seeded from `progress.md`, which counts against `max_rollovers` (2). After `max_rollovers` the step stops for a human to split it. `default_window_tokens` (200000) is the window the runner assumes for a model whose window it doesn't know, when it reads a session's context use. `gate_output_lines` (200) is how many of the last lines of each gate's output the runner keeps. `autocompact_env` (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`) names the variable that passes `autocompact_pct`, and `progress_file` (`runs/{run}/progress.md`) is the notes file a session keeps for its successor.
- `context.run_brief`: on by default. A Claude run session gets the stable text of its phase and role as a byte-identical appended system prompt that later sessions read from cache: the repository's rules (`project.agent_rules`), the skill and `brief:` files the step names as of the run's fork commit, the engine preamble and the result contract. It is for Claude only: sizers, the retro and Codex get no brief. When the brief cannot carry the rules, the session falls back to today's behaviour and Claude loads its own memory files: an `@` import in a rules file (anything outside code, even a bare `@README`), a committed `.claude/CLAUDE.md`, `.claude/rules/**`, a `CLAUDE.md` below the root or a `CLAUDE.local.md` anywhere (names matched with their case folded, so `claude.md` counts), a committed root `CLAUDE.md` that `agent_rules` does not list, or a tree at the fork commit too large to list within bounds. A pack override of `_preamble.md` or `_result.md` is read from the fork commit too: one the commit does not have, or one that holds a placeholder a brief cannot fill, gives the session no brief. A brief that is over its size cap, or cannot be built or written, shows as `brief_skipped` on `agent_started` and the prompt is built in full. A session keeps the brief it started with (the pin on its step, bound to that session), so switching `run_brief` off does not change a session in flight; a resume whose brief can't be rebuilt to its pin, or whose pin is malformed or another session's, starts a fresh session instead (`brief_replaced`), carrying the message the old one was about to get. While the brief carries the rules, run sessions also skip your personal `~/.claude/CLAUDE.md`. `validate` warns for each reason above it can see at `HEAD`. Known limits: the variable that keeps Claude from loading the memory files also drops organisation-managed memory and user rules, not only `~/.claude/CLAUDE.md` (read from the CLI's bundle, not probed); when the brief can't be built, written or verified, the session falls back to Claude loading `CLAUDE.md` from the worktree itself, which an agent that deliberately forces that fallback can exploit; and a resumed session keeps the system prompt it started with whatever file a resume passes (measured). Not protected.

While the sync is on, `validate` wants a lane of the pack, a `dashboard.backlog.module_lane` (a warning without one), and, when a synced issue can land in the `module_lane` of a capability map, a `dashboard.backlog.module_row`. Not protected.
- `issues.lane_labels`: issue label → lane for a synced issue, `{bug: bug}` by default; the first entry whose label the issue carries wins, compared without case. `validate` wants each label shaped like `in_progress_label`, and while the sync is on warns about a lane the pack doesn't have (that entry is ignored). `{bug: null}` drops the default. Not protected.
- `policy.enforce`: `report` (the default) or `block`; `validate` wants one of the two, and the audit treats any other value as `block`. It is the mode of the conformance bar a finished run is held to. Protected: a Settings page that could relax the bar would defeat it, and it is never a user key.
- `policy.obligations`: what a finished run must show evidence for, a mapping from a stable id to `{require: [...], when: <condition>, lanes: [...]}`. The layers merge it by id, and each entry replaces the entry of the same id whole. The engine ships `verified`, `reviewed`, `plan_approved` (feature lane) and `red_then_green` (bug lane); a pack adds its own, and `<id>: null` switches a default off, which `validate` reports as a warning. `engine_floor` (`gates:verify`) is added after the layers merge and no layer can remove or replace it. `when` names a condition, and an unknown result counts as holding. `lanes` filters like a step's `lanes`, and an absent one means every lane. `validate` checks that `when` is a known condition, that each `lanes` entry of an obligation the pack writes is a lane, that each `require` item parses, and that it names something this pack has; an engine default that names a step the pack's workflow lacks is an error that says to set it to `null`, and an engine default `approval:<phase>` naming a phase without `needs_approval: true` is a warning (set it to `null` to silence it). Protected. Each `require` item is one of:

  | Evidence | Satisfied when |
  |---|---|
  | `gates:<set>` | every gate in `gate_sets.<set>` has a passing (or skipped) full-tier result on the final tree, or a full-tier pass whose input hash equals the gate's input hash on the final tree. An affected-tier result (`tier: "affected"`), passed or skipped, never counts |
  | `step:<id>` | the step finished after the last code change, with no blocking finding left (or a human approved the phase after them). A step's own commit is not a later change, nor is a commit whose step ran every gate of `gate_sets.verify` (a refine-round fix); a conflicted merge of the base branch always is |
  | `approval:<phase>` | a human approved that phase (a phase with `needs_approval: true`), or its artifact was already on the base branch |
  | `expect:red_then_green` | the bug lane's regression test was seen red, then green, after the last code change (the same exceptions as `step:`) |

- `gates`: names to shell commands, with `cwd`, `when_exists`, `baseline` and `agent_check`. Protected.
- `gates_confirmed`: `true` once a human has checked `gates` and `gate_sets`, whether the pack wrote them or inherited them from a starter or the engine. Anything but `true` (absent included) is a `validate` warning, "detected or inherited gates are a proposal"; a value that is not a bool is an error. It is a bool, not bound to the commands that were confirmed: when an engine upgrade changes a starter's gates, `validate` does not ask again, so the release notes of an engine that changes a starter must say so. Protected, so the Settings page cannot confirm for you.
- `gates.<name>.baseline`: `red` records that the gate failed on `project.base_branch` when the pack was set up, and is a `validate` warning ("`<gate>` failed on `<base_branch>` when the pack was set up: fix it and remove `baseline`, or delete the gate"); `green` is allowed; any other value is an error. Protected, as `gates` is.
- `gates.<name>.cwd`: the directory a gate runs in, relative to the run's working directory (the worktree root when unset). It must be relative with no `..` part, otherwise `validate` refuses it. Protected, as `gates` is.
- `gates.<name>.agent_check`: `true` lists the gate in the build prompt as a check the implementer runs itself before writing its result (the `{self_checks}` placeholder). Only for a fast gate, such as a linter, a formatter check or a type checker, never a whole test suite. The runner still runs the gate afterwards. It needs a one-line `run` with no backtick and no `cwd`, otherwise `validate` refuses it. Default `false`. Protected, as `gates` is.
- `gates.<name>.group`: a name (1-40 letters, digits, `_`, `.`, `-`). Gates of different groups run at the same time, each group in its own thread and in set order inside it; every gate still runs after a failure, and the results keep the set's order. Gates with no `group` form one group of their own and run in order, as before, so a pack that sets none behaves as it always did. A `group` on a `setup` gate is a `validate` warning (setup gates start things in order). Only for gates that do not share a file, a port or a database. Default none. Protected, as `gates` is.
- `gates.<name>.resource`: a name (same shape as `group`). Two gates with the same `resource` never run at the same time, whatever their groups. The lock holds within one run; locks across runs come later. Default none. Protected, as `gates` is.
- `gates.<name>.inputs`: a non-empty list of globs (matched as `guards.path_matches` does: `**` crosses `/`, `*` and `?` do not), each a relative path inside the repository with no `..` part, naming the files the gate reads (for example `["api/**", "pyproject.toml"]` for `api_tests`). The gate's input hash is the gate's command digest plus the mode and blob of every file of the tree that the globs match, untracked files included. A gate that passed on another tree of the run is not run again when its input hash is the same: its fresh `gate_result` carries the `input_hash`, and a pass taken from another tree is told in a `gate_cache_hit` event (`gates_reused` still names it). `conformance` accepts such a pass as `gates:verify` evidence on the final tree only when the gate's input hash on that tree equals the result's, so the floor holds with no weaker evidence. Ignored files (`.env`, `node_modules`, build output) are not in the hash: a gate that reads one must not declare `inputs`, and neither must a gate whose result depends on anything the globs do not name. Once any gate declares `inputs`, `validate` warns about each `gate_sets.verify` gate without them ("`<gate>` has no `inputs`, so it runs again after every change"); a pack that declares none stays at 0 warnings. Default none (the gate is reused only on the same tree). Protected, as `gates` is.
- `gates.<name>.affected`: `{run, paths}`, the command a `gate_tier: affected` step runs instead of `run`, on the files it changed, for example `{run: "pytest {paths}", paths: ["tests/**/test_*.py"]}` for `api_tests`. `paths` is a non-empty list of relative globs with no `..` part (matched as `inputs` are), and defaults to the gate's `inputs`, else `["**"]`. `run` is a non-empty command whose only placeholder is `{paths}`, which becomes the changed files the globs match that still exist inside the worktree, each shell-quoted and prefixed `./` when it starts with `-`, joined by spaces; write a literal brace as `{{` or `}}` (so `${HOME}` is `${{HOME}}`). `{paths}` must be its own unquoted word: never inside `'...'`, `"..."`, `$(...)` or `${...}`, never after a here-document `<<`, and with only whitespace or the start before it and whitespace, `;`, `&`, `|` or the end after it, so each name stays one inert argument. A template is also refused when its quoting cannot be read with certainty: a backslash before `{paths}`, a line continuation (a backslash at the end of a line) anywhere but right after a blank, since the shell deletes it before it reads tokens and could join `$` and `(`, `'` or `{`, or `<` and `<`, any backtick (write `$(...)`; the shell ignores a `'` when it looks for the closing backtick), `$'...'`, `$[` or `((` (arithmetic), a `${` not written `${{`, a `$(` or `${` opened inside `"..."`, an unquoted `#` anywhere but right after a letter, a digit or one of `_-./=:+,@%` (so a comment is refused, including one right after `;`, `&`, `|`, `(`, `)` or a line continuation), a `#` or an unquoted `(` inside `$(...)` or `${...}`, or a quote or `$(` left open at its end. The names are inert only as long as the template leaves them as arguments: `eval`, `sh -c`, `xargs sh -c`, `alias` and `trap` parse them again, and what they then run is the template author's responsibility. `validate` refuses any other placeholder, a `{paths}` that breaks that rule, an empty command and a bad glob, and the runner runs the whole `run` for such a template. With `cwd` set, each path is made relative to it and the ones outside it are dropped. A deleted file, an absolute path, a path with a `..` part or a control character (a newline included) and a symlink out of the worktree are never passed. No matching path skips the gate ("no affected paths"), and more than 200 matching paths, or a rendered command over 64 KiB, run the whole `run` instead, as an ordinary full-tier result, so the argument list stays bounded. An affected-tier result is written with `tier: "affected"`: it is never reused, never `gates:verify` evidence and not a `full_suite_runs` batch, so the full set still runs on the final tree. A gate without `affected` runs its `run` at either tier. Default none. Protected, as `gates` is.
- `gate_sets`: named lists of gates; `verify` is required. Protected.
- `guardrails`: `forbidden_paths`, `reject_trailers` and `user_only_skills`. Protected.
- `overlays`: named overlays, each with `when_paths` (globs of changed paths), `when_keywords` (words in the plan) and `add_skills` (a role mapped to a skill). The engine acts on `security`: while the pack's `security_path` condition holds, it appends `add_skills` to the prompts of those roles and its `review_agent` runs the `security_review` step with `--agent <name>` (with `agents.claude.user_settings: false`, `validate` warns when `.claude/agents/<name>.md` is missing). A plan task whose own files match `security.when_paths` is sized up by itself, and keeps a `high` per-task review under a route profile. An `eval` overlay's `when_paths` makes `agentflow next` name the eval lane for uncommitted changes under them. The engine defaults have none. Protected.
- `conditions`: named checks the runner evaluates from files and git; `modules_done` reads `work_source` and takes no `from`. `finish` also runs the `eval` gate on a merged tree when the pack defines `eval_required` and it holds. Protected.
- `lanes`: the kinds of work. Not protected. - `record_step`, `resolve_step`: the steps that file a spec-gap answer and resolve a stop. Protected.
- `retro_step`: the one session of a retro run (`agentflow retro`), `{id: retro, skill: agentflow-retro, role: review, prompt: retro.md}` from the engine defaults. It reads the digest, proposes lessons, config notes and engine issues in its result, and changes no file; the runner checks every source and opens the draft pull request. Not a workflow key, so a pack that writes its whole workflow keeps it; `validate` checks it as it checks `resolve_step`, and refuses a lane or a phase named `retro`. Protected.
- `autonomy`: what the runner decides by itself. Not protected.
- `autonomy.answer_recommended`: `true` (the default) lets the runner take a `needs_human` result's recommended answers in **every** phase, `resolve: true` or not, parked or not, when each question has exactly one recommended option and none has a kind in `human_question_kinds`. It records them as `hitl_answered` with `by: runner`, notifies one line ("took the recommended answer(s) q1=A in plan/plan; the decision is recorded"), files a `spec_gap` answer in the spec through `record_step` as a human's answer is, and lists each one under "Decisions the runner took" in the pull request. A step that asks a question the runner already answered on it goes to a human. `false` sends every question to a human. A value that is not a bool is a `validate` error. Not protected.
- `autonomy.non_blocking_severities`: the severities a finding may have and still let a phase go on, `[minor, low, info, nit]` by default. Engine floor: `critical`, `high` and `medium`, an empty severity and a missing one always block, so the code ignores such an entry and `validate` refuses a list that names one (or `none` or `null`) or is not a list of strings. Not protected.
- `autonomy.finding_rounds`: how many refine rounds the runner opens by itself on a phase's blocking findings before they go to a human, `2` by default. Engine floor: at least 1, so automatic refinement can't be switched off. A value below 1 is a `validate` error and the Settings form refuses it, and a pack that writes its own `phases:` and so drops the block still gets 1 round. Not protected.
- `autonomy.resolve_kinds`: the stop kinds a `resolve: true` phase sends to a resolver session before a human, each with how many resolver sessions it gets (at least 1). The defaults: `blocked`, `blocked_repeat`, `step_timeout`, `gate_failed`, `fix_attempts_exhausted` and `red_test_passes` 2 each, and `review_unresolved`, `turn_cap` and `budget_cap` 1 each. A kind that is left out goes to a human at once, and some never go to a resolver: `budget_exceeded`, phase approvals, checkpoints, `condition`, `max_rounds`, `agent_unavailable`, `conformance_failed`, `reconcile_changed_conditions`, `preflight_failed` and `environment`. A stop of the resolver's own session is always a human's. Not protected.
- `autonomy.revert_forbidden`: in a `resolve: true` phase, how often per step (counted since a human last settled it) the runner puts back a change to a forbidden path by itself and tells the step, before the next one is a `guard_violation` for a human; `1` by default, `0` never. Not protected.
- `autonomy.human_question_kinds`: the question kinds only a human answers, `[boundary]` by default (`boundary`: the repository's docs reserve the decision for a human, such as an "ask first" or "never" rule). One such question makes its whole set a human's in any phase, parked or not. `[]` lets the runner answer every kind. A list of the kinds `spec_gap`, `ambiguity`, `conflict`, `review_dispute`, `boundary` and `other`, or `validate` refuses it. Not protected.
- `route.mode`: `"off"` (the default; quote it, since YAML reads a bare `off` as `false`), `observe` or `on`. `off` sizes nothing. `observe` decides a profile for each run of a route lane and records it, and the run still walks the full route. `on` applies the profile. Any other value is a `validate` error and runs as `off`, and `observe` or `on` with no profiles is a warning ("every profile runs the full route"). The Settings form edits it.
- `route.lanes`: the lanes whose runs are sized, `[feature]` by default. Each must be one of `lanes`, or `validate` refuses it. A run of any other lane never pays a triage session. Protected.
- `route.profiles`: the profiles `XS`, `S`, `M` and `L` (smallest first; any other name is a `validate` error), each with up to three keys: `skip`, a list of `<phase>/<id>` entries naming top-level steps the route drops; `doubt_rounds`, a map of a phase to the most doubt rounds it gets (a whole number of at least 1, since the engine floor keeps at least one round); and `per_task_review`, `true` or `false`, which turns the per-task review of the build off. Engine floor: a `skip` entry may not name a `finish` or `ci` step, a `foreach` step or a step that is `step:<id>` evidence of an obligation covering a route lane, nor a group or repeat that holds one (its nested steps and `review` steps count), and a profile may not skip every step a route lane walks in a phase whose `approval:<phase>` an obligation requires; each of those is a `validate` error that says which obligation or step it would drop, and the runner never skips a `finish`, `ci` or `foreach` step whatever the profile says. The engine's grid is `XS: {skip: [define/grill_open_questions, define/spec_review, plan/plan_review], per_task_review: false}`, `S: {doubt_rounds: {define: 1, plan: 1}, per_task_review: false}`, `M: {doubt_rounds: {define: 2, plan: 1}}` and `L: {}`. It names steps of the engine's workflow, so a pack that writes its own `phases:` drops the grid and writes its own `route` (a pack with no `route` has none, and `mode` is `off`). Protected.
- `ci`: polling and fix rounds of the `ci` step: `poll_s` (60, seconds between reads of the PR's checks), `appear_min` (5: no checks at all for this long is a stop), `timeout_min` (45: checks still pending after this are a stop, or a watch), `fix_rounds` (3 fix sessions for failing checks), `rerun_rounds` (1: a fix session that changes nothing reruns the failed jobs this often) and `sync_rounds` (2: at `finish`, resolver sessions for the target branch's conflicts, and re-syncs while GitHub still reports one). `ci.watch_max_h` (`0`, off, by default; at most 720) is how many hours the run watches checks still pending after `ci.timeout_min` before the `ci_failed` stop: the run is held (`ci_pending`), a `gh` error or no checks during the watch is no verdict, and its time is `ci` time in `metrics`. A run watching CI holds no queue slot, so a pack whose runs share one database or port should leave it at 0 until slots exist (T6). A resume starts a fresh watch, after `ci.timeout_min` again. A pack that writes its own `ci` block may leave the key out, which is off. Not protected.
- `ci.early_pr_after`: `""` (the default, off) or a phase that comes before the phase holding the `finish` step; `validate` refuses any other phase. When that phase is approved, the runner pushes the branch by its commit and opens the draft PR (`pr_opened` with `early: true`, key `<phase>/early_pr`, the body's first line saying review is still running), so CI runs while review does. A push before the audit is a draft only: `finish` still runs the conformance audit on the final tree, then pushes it and updates the PR's description (`pr_updated`) instead of opening one, and marking the PR ready still needs that audit and a green CI: the `ci` step watches an early PR only once `finish` has updated it, and reads its checks only while GitHub's head for it is the sha the runner pushed last, the merge `finish` pushes again for a conflicting PR included. CI is never evidence for `gates:verify`. A dirty tree, a commit the runner did not make, a failed push or a failed `gh pr create` at that point is `early_pr_failed`, never a stop, and `finish` opens the PR as usual. Nothing happens on the base branch, for a lane with no `finish` step, or for a run whose `--to` ends before it. A pack that writes its own `ci` block may leave the key out, which is off. Not protected.
- `phases.<name>`: the workflow. Protected, except `needs_approval`, `resolve`, `model` and `agent`. A phase has `needs_approval` (required: `true` stops for a human once it ran), `resolve` (`true` sends its stops to `resolve_step` first, which then must exist), `model` (a model, or a map by role with a `default`), `agent` (one of `agents`, enabled), `skip_if` (a condition that skips the whole phase), `approval_note` and `steps`.
- `phases.<name>.approval_note`: `{when: <condition>, human_skill: <skill>}`, a line on the phase's approval page, when the condition holds, that offers a skill for the human to run before approving; the runner never runs it. `human_skill` must be in `guardrails.user_only_skills`, or `validate` refuses it. This pack offers `doubt-driven-development` on `plan` when `security_path` holds. Protected with the rest of the workflow.
- `phases.<name>.steps[]`: one entry per step. Every step has an `id`, and an agent step a `skill`, a `role` and a `prompt`. The other keys: `type` (`agent`, the default, or `gate`, `group`, `checkpoint`, `finish`, `commit`, `ci`), `lanes`, `when`, `unless`, `next`, `output`, `brief` and `task_briefs` (files the prompt carries), `model`, `gates`, `fix_loop`, `gates_first`, `checks`, `on_fail`, `expect` (`red` or `green`), `commit`, `message`, `review`, `foreach` (`plan_task`), `batch`, `small_plan`, `carry`, `steps` and `repeat` (a `group`'s), `wait_for` and `name` (a `checkpoint`'s), `sync` (a `finish` step's), `fix` and `forbid` (a `ci` step's), `human_paths`, `tdd`, `gate_tier`, `max_turns`, `reconciles` and `blocks_on_findings`. Any other key is refused when the config loads. `explain` and the defaults file show them in use. Protected with the rest of the workflow.
- `phases.<name>.steps[].max_turns`: this step's own turn cap, over its role's (`agents.claude.max_turns_by_role`) and `agents.<name>.max_turns`; a whole number of 1 or more, or the config refuses to load (`0` is never "no cap" here). A doubt review after the first round gets half of it. It also applies to `record_step`, `resolve_step` and `retro_step`. Protected with the rest of the workflow.
- `phases.<name>.steps[].carry`: `{max_tasks, max_context_pct}` on a `foreach: plan_task` step. The next task's implementer resumes the previous task's session (at that session's effort, with its brief) when all of these hold: the previous task ran in the same walk of the plan and was committed in round 0 with no stop or park on any of its steps and no task held in between; the session holds fewer than `max_tasks` tasks; its last turn was below `max_context_pct` of the context; it hasn't rolled over or compacted; the plan sizer didn't flag the next task `risk` or size it above the session's effort. Otherwise the task starts fresh, as before. Tasks in a batch and in an active small plan keep their own sharing and never carry; a refine round never carries. The reviewer of every task stays fresh, and every task keeps its own gates, guards and commit. Each decision is recorded once per task, as `session_carried` (`tasks`: the session's count) or `carry_declined` (`reason`: `no_session`, `not_clean`, `max_tasks`, `rolled_over`, `compacted`, `context`, `risk` or `effort`), and a restarted runner takes the recorded one. Default `{max_tasks: 1}` (off; nothing is recorded), and `max_context_pct` 40 when left out. `max_tasks` is a whole number of 1 or more and `max_context_pct` a number from 10 to 70; any other value, another key or `carry` on another step is refused when the config loads. Protected with the rest of the workflow.
- `phases.<name>.steps[].gate_tier`: `full` (the default) or `affected`. The gates run at three tiers: the `build` set is the fast tier, run on every task; `affected` is for the steps that fix things, which run each gate's `affected` command on the files they changed (an agent step's gates, on the paths changed since the commit the step started on, and a `finish` step's `sync` merge check, on the paths the merge changes against the branch; the `eval` gate always runs in full); and the `verify` set runs in full once, on the final tree, which the conformance audit requires. The engine defaults set `affected` on `review/fix_findings` and `ship/finish.sync`, which changes nothing until a gate declares `affected`. `ship/ci.fix` stays `full`: the `ci` step pushes right after its fix and no conformance audit follows, so a pack may set `gate_tier: affected` on `ci.fix` only if it accepts that the pushed fix is not covered by a full local verify. `validate` refuses any other value, and `affected` on a step with no `gates`. Protected through `phases.<name>`.
- `phases.<name>.steps[].reconciles`: `true` marks the step that revises a phase's artifact after the phase's review found fault with it. It must be a boolean on a top-level `agent` step that has an `output` and `commit: true`, no `gates` (a reconcile step runs no gates and its agent runs no commands: it edits only its `output`), and not `role: review`; `validate` refuses it on a nested step and on `record_step`, `resolve_step` and `retro_step`, and refuses two for one lane in a phase or one after a `blocks_on_findings` step of its lane. It warns about a reconciles step in a phase with `needs_approval: false` or with no `blocks_on_findings` step, since it never runs there. Protected through `phases.<name>`.
- `phases.<name>.steps[].blocks_on_findings`: `true` lets the step's blocking `findings` hold the phase back. In a `needs_approval: false` phase they open the runner's refine rounds; in a `needs_approval: true` phase they go to the approval page, and `validate` warns when such a phase has no `reconciles` step to settle them first. Protected through `phases.<name>`.
- `phase_approval`: the refine prompt and what an approval page shows. Protected.
- `checkpoints`: who answers each inner checkpoint. Not protected.
- `hitl`: notifications, reminders and where decisions are recorded. Not protected, except `hitl.notify`. The engine defaults set none of its keys.
- `hitl.notify`: a list of notifiers, each `{type, enabled}` (`enabled` defaults to `true`): `terminal_bell`, `macos` (`osascript`, with a `title` in which `{run}` is the run id) and `webhook` (a JSON `{title, message}` POST to the URL in the environment variable `url_env`). A failing notifier is recorded as `notify_failed` and never stops a run. Protected; the user file may set it.
- `hitl.remind_after_h`: hours a run may wait on a person before it is notified again, while `agentflow queue`, the dashboard or a `--watch` view runs; unset means no reminder (this pack: 4). Not protected; the user file may set it.
- `hitl.record_decisions`: where a human's answer to each question kind is kept: `record_step` (filed in the spec as its own `Decide …` commit) or `commit_body` (in the step's commit body). The engine's choice is `spec_gap: record_step` and `ambiguity`, `review_dispute` and `boundary`: `commit_body`. Not protected.
- `hitl.park_independent`: `true` parks a plan task whose question later tasks can go on without (section 8), and runs the tasks that don't depend on it; off when unset. Not protected.
- `dashboard`: host, port and the Backlog. Not protected, except `dashboard.host`. `dashboard.host` (`127.0.0.1`) and `dashboard.port` (7788; the user file may set it, and the server takes it on restart). `dashboard.show_done_days` (0, every finished run kept) is how many days a Done card stays on the Board. `dashboard.agents.show_exited_min` (10) and `dashboard.agents.idle_warn_min` (5) are how long the Agents view lists an exited agent and when it flags an idle one. `dashboard.backlog` takes `module_lane` (the lane that starts a work-source module), `lane_labels` (a lane mapped to the plain words the page shows for it, as in "What kind of work?"), `new_task` (each lane mapped to its New task form's fields, from `issue`, `task`, `topic`, `new_module` and `after`), `module_row` (a new capability-map row's cells by column header, with `Module id` and `Depends on`) and `sync_base` (`true` fast-forwards the local base branch from `origin` before a Backlog card starts a run; it never rewrites history); any other key is a `validate` error. `dashboard.board_refresh_s` (2 by default, 0.5–60) is the most often the page refetches the Board while events arrive. `dashboard.done_shown` (10 by default, 1–1000) is how many Done cards the Board draws, newest first, before **Show all (N)**. `show_done_days` still decides which finished runs are kept at all. `dashboard.artifact_max_kb` (512 by default, 16–8192) is the largest spec, plan revision or diff the page loads; above it the page shows the head and says so. `dashboard.inbox_legacy` (false by default) also shows the old Needs-human list at the bottom of the Board; the Inbox tab stays. It is a fallback for one release. `dashboard.backlog.new_task` may list `issue` for the `module_lane` too; in a capability map that needs `dashboard.backlog.module_row`, since such a card adds the row `issue-<N>`.

## 15. Lessons and retros

A lesson is a one-line rule that earlier runs taught, such as "run the unit tests before writing a build step's result". Every agent session's prompt carries the lessons under "Lessons from earlier runs". A **retro** reads the runs that ended since the last retro and proposes lessons as a draft pull request. The pull request changes only `.agentflow/lessons.md`, and a human merges it or closes it. The runner never writes a lesson into the repository on its own, and it never merges.

There are two layers of lessons:
- **The engine's `agentflow/lessons.md`** holds rules that hold in any project, with ids `E-NNNN`. It ships with the engine and changes only in an engine release. Its lessons have no `review_by`, so they never expire.
- **The pack's `.agentflow/lessons.md`** holds this repository's rules, with ids `L-NNNN`. A merged retro PR or a human changes it. Its path is fixed (there is no config key), it is under the engine floor (`.agentflow/**`), so no agent in a run can edit it, and only the main checkout's copy is read.

A step gets the lessons for every phase plus those whose `applies` names its phase, engine lessons first, and none that is past its `review_by`. The slot holds at most `memory.lessons_max_tokens` (1500 by default; 0 turns lessons off). Over that, the lowest-numbered pack lessons are dropped first, the engine's last, and the run records `memory_truncated`. Each fresh session records which lessons it carried (`lessons_injected`). A result may list the ones it used in `lessons_cited`, and the runner records each as `lesson_cited`.

The conformance audit at `finish` (section 14, `policy`) adds two signals, `conformance_missing` and `conformance_waived`: the obligations that had no evidence, or were waived, at the run's last audit. They reach the retro's digest like every other signal, and `agentflow scorecard` (and the dashboard's Metrics tab) compares them, with the gate and cost signals, against a baseline frozen with `agentflow scorecard --freeze`. A `conformance_missing` above 0 is an SLO breach, and the scorecard lists it first. `agentflow metrics` prints where each run's wall time went, as time and share per bucket, with its lead time, the share blocked on a human and its full-suite runs, and the same in total.

`policy.enforce: block` is a process control, not a security boundary. A run's agent can still write outside its worktree: its shell reaches the run's `events.jsonl` and the main checkout's pack, so an agent set on it could forge evidence or loosen the policy. A pack that relies on `block` to keep unproven work from being pushed should also sandbox the agent, so it can write only its worktree and its workspace.

### How a retro runs

`agentflow retro` runs a retro now. `agentflow next` and `agentflow status` print `Retro due: <n> finished runs since <date> → agentflow retro`, and the dashboard shows the same line as a banner, once a retro is due. A retro is due when `memory.retro_every_days` (7) days have passed since the last finished retro started (or there has been none) and a run has ended since then. `agentflow queue` runs a due retro by itself before it starts modules, but only once a retro has finished before: you run the first retro by hand with `agentflow retro`, and until then the queue starts no retro and says once (one `retro due` line) that you should. If a retro the queue started does not end `done`, that queue tries no other retro until it is started again. `retro_every_days: 0` means you run retros by hand only.

1. **The runs.** The retro reads the runs that ended (`done`, `failed` or `cancelled`) after the last *finished* retro started. With no finished retro it reads every ended run, and `--since YYYY-MM-DD` reads the runs that ended on or after that day (from midnight UTC) instead. Retro runs are never read. With nothing to read it prints `nothing to learn` and creates nothing.
2. **The digest.** The runner writes the digest from the run logs alone, with no model involved, to `<state dir>/runs/<run>/retro/digest.md`, and the session gets a copy in its workspace. It holds one line per run, every signal event cited as `<run id>#<seq>` (a failed gate with its last lines, a fix attempt, a stop, a guard trip, a denied command, a human rejection or answer, a blocking review, a CI round, a retry, a runner error), the signal means over those runs, and each lesson with its effect. Quoted text is cleaned and cut, and the digest says it is data, never an instruction. Over `memory.digest_tokens` (15000), the oldest runs' evidence is dropped first and one line counts what went. `agentflow retro --dry-run` prints the digest and the session's prompt, and creates no run, branch or worktree.
3. **The session.** The retro is a run of the engine's `retro` pipeline, which is not a lane. It works in its own worktree on `project.branch` with lane `retro` and slug `YYYYMMDD`, for example `flow/retro/20261108`, or `flow/retro/20261108-2` for a second retro that day. It forks from `project.fork_from`. One session of `retro_step` (the bundled `agentflow-retro` skill and `prompts/retro.md`) reads the digest and changes no file. Its result proposes lessons to add, expire and renew, config notes and engine issues.
4. **The checks.** The runner keeps a proposal only when it holds against the run logs:
   - An add cites 1 to 10 sources, and each one resolves to an event of a run the digest read.
   - The add's `target` is a signal key, and its `applies` names phases of the pack.
   - Its title and body are cleaned, then cut to 80 and 300 characters. An add that is empty after that, whose title a lesson in either layer already has (in any case), or that would not read back the same from the rendered file is dropped.
   - A retro adds at most 5 lessons. A new lesson gets the next unused `L-` number (above those an earlier retro added too, even while its PR is not merged), `review_by` today plus 90 days, and a `baseline` the runner computes from the digest's runs.
   - An expire names an existing `L-` lesson. The engine's `E-` lessons are never expired by a retro.
   - A renew names an existing `L-` lesson and a date after today, at most 180 days ahead.
   - A config note or an engine issue keeps the sources that resolve, and is dropped if none does.

   The PR body's "Dropped" section lists every proposal the runner left out, with the reason.
5. **The pull request.** If nothing changed, the run ends `done` with `nothing to learn` and opens no PR. Otherwise the runner renders `.agentflow/lessons.md` and commits that file alone (`Update lessons from the retro of <n> runs.`). It pushes the commit by its sha to the same-named branch on `origin`, with no hooks, then opens a draft PR titled `Lessons from <n> runs (<date>)` against `project.fork_from`. The exit code is 0 when the retro run ended `done`, and 1 when it stopped, failed or was refused.

Only one retro is open at a time. While one is running, waiting on you or stopped on an error, `agentflow retro` is refused, the queue starts none, and no `Retro due` line shows. A retro interrupted by Ctrl-C, SIGTERM or SIGHUP ends `cancelled`, so it blocks no later one. (A `kill -9` or a crash cannot be caught: the retro stays `running` until you run `agentflow cancel <run>`.)

### What the runner refuses after the session, and why

The session is an agent with a shell, and "change no file" is only a request in its prompt. So the runner records the checkout before the session and compares it afterwards. It also reads the lessons file it builds on from git, at the commit the retro forked from, and never from the work tree. Each of these stops the retro as `blocked`, before any commit or push:
- **The git configuration, hooks or control files changed.** This covers every config scope, `origin`'s push URL, `hooks/`, `info/exclude`, `info/attributes`, `info/sparse-checkout`, `info/grafts`, and the worktree's links. These decide what the runner's own git calls do later: a push refspec could send the lessons commit to `main`, and a planted hook would run as you. Other branches' `branch.<name>.*` keys are ignored, so another run pushing at the same time does not trip it.
- **The tree changed.** This covers any new, changed or ignored file, an index entry flagged skip-worktree or assume-unchanged, and `HEAD` moved or pointed at another branch. The stop names the paths.
- **Something sits at `.agentflow/lessons.md` that the branch does not hold.** This covers a file the branch lacks, different bytes, a FIFO or a device, a symlink, or a hard link.
- **The commit is refused.** `gitops.commit_lessons` commits the lessons file and nothing else. It refuses any other path, a symlinked or hard-linked file, and a `guardrails.reject_trailers` trailer, and the committed blob must be exactly the text the runner wrote. After the commit, the git state and `HEAD` are checked once more before the push.

The retro also stops before its session when the lessons file on `project.fork_from` has a malformed entry (`agentflow validate` lists them), and after its session when that file is ignored by `.gitignore`, when the result cannot be read, or when `gh` cannot open the PR. In that last case the stop names the branch it already pushed.

**A stopped retro is cancelled and run again.** It shows in the inbox as `blocked` on `retro/retro`, with the reason. It cannot be approved, answered, rejected, retried or resumed, from the CLI or the dashboard. Read the reason, fix the cause (for example the malformed entry, or a hook or setting the stop names), then `agentflow cancel <run>` and `agentflow retro`. The new retro reads the same runs, because the stopped one never finished. After a stop that says it already pushed the branch (`gh` could not open the PR), cancelling it and running `agentflow retro` again pushes a new branch (with a `-2` suffix on the same day): delete the old remote branch by hand.

### Reviewing a lessons PR

The diff is `.agentflow/lessons.md` alone, and the runner refuses to open the PR otherwise. The body has these sections, in this order:
- **The lead paragraph** names how many runs the retro read (first and last run id). It says the runner checked every source against the run logs and that the numbers show correlation, not cause. When the digest was cut to fit, it says how many evidence entries were left out.
- **Effect of previous lessons** is the `agentflow lessons` table as it stood when the retro ran: each lesson's verdict, target, baseline, after and citations (see the next subsection).
- **Lessons** has one line for each change: `Added` (with its title, body, target, recorded baseline, phases, `review_by`, sources and whether it is an engine candidate), `Expired` and `Renewed`, each with its reason.
- **Config notes** and **Engine issues seen** are advice that nothing applies. A config note is a setting to look at (a budget, a model, a timeout, a slow gate). An engine issue is a runner bug to file.
- **Dropped** lists each proposal the runner refused, and why.

All the text the model wrote is in code spans, so it cannot add headings, links or mentions. Before you merge:
1. **Check the evidence.** Each source is `<run id>#<seq>`. Open the run with `agentflow status <run id>`, the dashboard's Run page (the Lessons tab links each source), or the `seq` line of the run's `events.jsonl`. Check that the event shows what the lesson claims.
2. **Check the rule.** It should be something an agent can do differently, not a one-off. A cause in a setting belongs in the config, not in a lesson.
3. **Check the target.** It should be a signal the rule should move, so that the next retro can tell whether the lesson helped. A lesson marked `engine candidate: yes` may hold in any project. Promote it by hand in an engine change to `agentflow/lessons.md`, which takes an `E-` id.
4. **Read Dropped.** Many dropped sources mean the session cited events that do not exist. Use it as a reason to read the rest more carefully.
5. **Edit or close.** Edit the PR branch by hand if a lesson needs rewording (keep the format below), or close the PR. Closing it changes nothing.

Merging makes the lesson live for every session that starts after it reaches the **main checkout's** `.agentflow/lessons.md`. Lessons are read from that file on disk, so after merging on the forge, run `git pull` in the main checkout.

### Reading `agentflow lessons`

`agentflow lessons` prints one row per lesson of both layers. The columns are `ID`, `VERDICT`, `TARGET`, `BASELINE`, `AFTER`, `CITED` and `TITLE`, and the title of a lesson past its `review_by` ends `(past review_by)`. A note under the table says that before/after shows correlation, not cause. `--json` gives the same data, plus each lesson's body, phases and sources. In it, `baseline` is the computed mean (the BASELINE column), and the `baseline` line recorded in the file is under `recorded_baseline`. The dashboard's Lessons tab shows it as a table, and each source opens its run.
- **AFTER** is the mean of the target signal over the ended, non-retro runs that carried the lesson.
- **BASELINE** is the mean over the ended runs without it that started before the first run that carried it. Each value has its count of runs.
- A run counts only when it has the target's key, such as `gate_first_pass:unit` for a run where gate `unit` ran. Likewise a `doubt_*` key exists only for a phase whose doubt review ran. A count signal (`fix_attempts`, `guard_trips`, `permission_denied`, `stop`, `human_rejections`, `refine_rounds`, `gate_reruns`, `effort_escalations`, `undersized`, `sizer_fallbacks`, `ci_rounds`, `rollovers`, `progress_not_updated`, `conformance_missing`, `conformance_waived`, `full_suite_runs`, `route_upgrades`, `compactions` and `usage_holds`) reads 0 in a run that has none.
- **VERDICT** is one of these:
  - `improved` or `worse`: the target moved by at least 10% the right or the wrong way. The change is relative to the baseline, or absolute when the baseline is below 1. Higher is better for `gate_first_pass`, `doubt_actionable`, `informed_approval` and `gate_cache_hit_rate` only; lower is better for every other signal.
  - `no change`: the target moved by less than that.
  - `too few runs`: fewer than 3 runs carried the lesson, or there is no baseline.
  - `not measured`: the lesson has no `target`, or one outside the vocabulary.
- **CITED** counts the times a session said it used the lesson.

The verdict is computed from the runs every time. The `baseline` line in the file is the record the retro wrote when it added the lesson, and editing it changes no verdict.

### The file format, and editing or expiring a lesson by hand

```
## L-0007 Run the portability test before finishing a build task
- applies: build, verify
- source: 20261105-0912-feature-pack#418
- review_by: 2027-02-01
- target: gate_first_pass:portability
- baseline: 0.33 over 9 runs to 2026-11-08
The portability gate fails on project strings in engine files; grep its denylist first.
```

An entry is a `## <id> <title>` heading, then any of the `- key: value` lines, then exactly one body line of at most 300 characters. Text before the first `## ` heading is the file's header and is not read.
- **`applies`**: phase names separated by commas. Leave the line out to cover every phase.
- **`source`**: `<run id>#<seq>` pointers separated by commas.
- **`review_by`**: a date, `YYYY-MM-DD`. On the day after it, the lesson leaves every prompt. It stays in the file, and the next retro's digest marks it expired, so the retro can renew or expire it.
- **`target`**: one signal key from the fixed vocabulary: `gate_first_pass:<gate>`, `fix_attempts:<phase>`, `guard_trips:<kind>`, `permission_denied:<tool>`, `stop:<kind>`, `human_rejections:<phase>`, `review_blocking:<phase>`, `cost_per_task:<phase>`, `turns_per_step:<phase>`, `gate_minutes:<phase>` (minutes the phase spent in gates), `refine_rounds:<phase>` (rounds the runner opened on its own findings), `gate_reruns` (gates run again on a tree they had already passed on, with the same command: it should stay 0), `effort_escalations:<phase>` (steps raised one level after a failed gate or a reopening review), `undersized:<phase>` (those escalations of a step the sizer had put at `low` or `medium`), `sizer_fallbacks:<phase>` (steps sized by `effort.default` because the sizer failed), `doubt_blocking:<phase>`, `doubt_rounds:<phase>`, `doubt_actionable:<phase>` (higher is better), `doubt_noise:<phase>`, `doubt_misread:<phase>` and `doubt_open:<phase>` (the doubt review's blocking findings in its first review, its reconcile rounds, the findings by disposition and those still open at the approval; a run with no doubt review has no such key), `informed_approval:<phase>` (higher is better: the share of a person's approvals of the phase that viewed every newest revision it produced on the dashboard; a CLI approval counts as not informed, and a phase that produced nothing has no such key), `ci_rounds`, `rollovers`, `progress_not_updated`, `rework_pct`, `conformance_missing` and `conformance_waived` (the obligations with no evidence, or waived, at the run's last conformance audit; a run with no audit has no such key), `gate_cache_hit_rate` (higher is better: the gates reused from a cached pass over those reused plus those that ran, 0..1), `lead_time_h` (hours from the run's start to its pull request marked ready; a run with no ready pull request has no such key), `human_blocked_share` (the share of the run's wall time spent waiting on a person with no agent or gate running), `full_suite_runs` (how many times the whole `verify` gate set ran in one batch with none of its gates reused from a cached result), `route_upgrades` (how many times the runner raised the run's route profile mid-flight; a run with no `route_profile` has no such key), `cache_write_share` (the cache-write share of the run's USD, 0..1; a run with no recorded usage has no such key), `prefix_write_tokens` (the median tokens a fresh session wrote to the cache for its prefix), `session_turns_p90:<kind>` (the p90 of a step kind's sessions' turns, such as `build.implement`; a kind with no turns has no such key), `tool_output_kchars:<kind>` (thousands of characters of tool output per session of the kind that reached the model; present for the kinds that have `session_turns_p90`), `compactions` (times a session's context was compacted) or `usage_holds` (times the run waited out a usage limit; a CI or outage hold doesn't count). The six cost signals, from `cache_write_share` to `usage_holds`, are lower-is-better, and their scorecard baseline starts at the first `agentflow scorecard --freeze` after engine 3.0. A lesson without a `target`, or with one outside this list, is `not measured`.
- **`baseline`**: written by the runner. It is a record, not an input (see above).

The rules for editing by hand:
- **Change it like code:** on a branch, through a PR, then pull it into the main checkout. An edit to the main checkout's file reaches the next session at once, committed or not.
- **Keep one body line** with no list dash or heading mark at its start. Never put ` #` (a space and then `#`) in a value, because it starts a comment.
- **Give a new lesson a number above every `L-` number used before,** including those of expired lessons. A lesson's effect is read from the runs that carried its id, so a reused id would inherit the old lesson's runs. The retro numbers its own adds this way.
- **A malformed entry is left out of prompts,** and `agentflow validate` names its line as a warning. A retro stops before its session when the file on `project.fork_from` has one, so fix it before the next retro. A duplicate id keeps the first entry. `validate` also warns about an `applies` phase the pack does not have and a `target` outside the vocabulary. It never warns about a passed `review_by`.
- **To expire a lesson,** delete its entry, or set `review_by` to a past date to keep it in the file for the record. **To renew it,** set a later `review_by`.
- **Edit the engine's `E-` lessons only in an engine change.** A retro never touches them.
